## Task


## 命名规范
统一项目全维度命名规则，全程遵循语义化、简洁化、标准化原则，杜绝拼音、缩写歧义、大小写混乱、无意义命名，适配Java官方编码规范及企业通用标准。
1. 项目/模块命名：采用小写字母+中划线方式，语义清晰，贴合业务场景；
2. 包命名：层级清晰，统一小写，遵循分层分包规则，无冗余层级、无跨层乱包；
3. 类命名：大驼峰式，名词为主，精准标识类职责（如Controller、Service、Mapper、Entity等后缀统一），严格遵循单一职责；
4. 方法命名：小驼峰式，动词+名词结构，精准描述方法功能，禁止模糊命名；
5. 变量/常量命名：变量小驼峰、常量全大写+下划线分隔，语义唯一，杜绝全局万能变量；
6. 数据库命名：库、表、字段统一小写+下划线，表名贴合业务，字段语义清晰，禁止保留字；
7. 接口/枚举/自定义异常命名：统一专属后缀，语义明确，风格统一。所有命名做到见名知意，适配代码复用与后期维护。


## 架构设计
1. 整体架构分层：按照Controller（控制层）、Service（业务层）、Mapper（数据层）、Entity（实体层）四层标准架构开发，分层边界清晰、职责绝对单一，禁止跨层直接调用、层级混乱；
2. 设计原则落地：所有代码、类、方法设计必须贴合六大设计原则（单一职责、依赖倒置、开闭原则、里氏替换原则、迪米特法则、合成复用原则）和26种软件设计模式，杜绝大类、万能方法、强耦合代码，子类可完全替换父类、抽象与实现分离、模块最小依赖、优先组合复用而非继承，以高内聚、低耦合为核心，保障项目极致的扩展性、复用性、可维护性；
3. 包结构规范：分包清晰、层级固定，按业务模块+分层维度拆分，公共组件、工具类、全局配置、异常、枚举统一独立分包，无无效包、无冗余层级；
4. 依赖管控：禁止循环依赖、无效依赖、过度依赖，依赖关系单向流转，上层依赖下层，下层不依赖上层；
5. 拓展性设计：架构预留业务拓展、功能迭代、模块拆分的空间，支持后续新增业务、接入中间件、分布式改造，无需大幅重构原有代码；
6. 复用性设计：公共能力、通用逻辑、基础功能统一抽象封装，形成通用组件，全项目复用，减少冗余代码；
7. 可维护性设计：代码结构规整、逻辑清晰、注释完善，报错定位快速，迭代修改无副作用，降低后期运维成本。

## 接口规范
1. 接口路由：统一版本管控，路由层级清晰，语义规范，禁止随意定义不规则路由；
2. 请求方式：基于RESTful风格，严格区分GET（查询）、POST（新增）、PUT（修改）、DELETE（删除），请求方式与业务动作匹配；
3. 参数规范：区分路径参数、请求参数、请求体参数，入参统一校验，禁止参数冗余、参数滥用。对于接口参数接收只有一两个参数，主要使用路径参数的方式，如果有必要进行后续扩展，则可以直接使用实体类作为接口参数。使用了实体类后，尽量使用分组进行参数校验，进行实体类的复用。路径参数要添加对应的Swagger3的注解信息，JSON体则要添加对应的@Validated注解，在所有的dto与vo对象中，添加对应的Swagger3的注解信息；
4. 统一响应格式：封装全局统一返回体，包含状态码、提示信息、业务数据、时间戳等固定字段，成功、异常返回格式统一；
5. 分页、排序、查询条件统一封装通用DTO，复用通用工具方法，杜绝重复代码；
6. 接口职责：Controller层仅负责参数接收、校验、日志记录、业务层方法调用、响应返回，不处理核心业务逻辑，严格分层解耦；
7. 接口文档：所有接口必须使用Swagger3+knife4j技术，标注完整注释，说明功能、入参、出参、异常场景，适配团队对接与后期维护。

## 业务编排
1、分层职责：Controller层负责请求转发、参数校验、响应封装；Service层承载核心业务逻辑，区分通用业务与特殊业务；ServiceImpl实现具体业务，严格单一职责，一个业务类仅负责对应模块业务；Mapper层仅负责数据持久化，如有必要可以使用DDD架构设计；
2、业务解耦：复杂业务拆分单一原子方法，禁止超大单体方法、超大业务类，遵循迪米特法则，减少模块间依赖；
3、复用设计：通用业务逻辑、公共方法统一封装工具类、通用Service，杜绝重复编码，提升代码复用性；
4、拓展设计：业务新增、迭代修改遵循开闭原则，优先扩展新增类/方法，禁止随意修改原有成熟核心代码；
5、依赖规范：遵循依赖倒置原则，依赖抽象而非实现，通过接口定义业务规范，实现类灵活替换；
6、事务编排：增删改核心业务统一配置事务，事务粒度精准控制，避免事务过大、过小导致的数据不一致问题，支持事务回滚、异常兜底；
7、逻辑兼容：业务迭代预留拓展空间，兼容新旧业务逻辑，避免硬编码、写死参数。
8. 代码实现：尽量使用stream处理数据，使用hutool工具类提高开发效率。Service层中的方法实现，优先将参数实体类中的字段进行变量获取获取，而不是后续直接使用这个实体类进行获取，除非后续只是使用hutool的复制类操作，则可以不进行这个操作

## 数据实体与访问控制
1. 实体分层规范：严格区分Entity（数据库映射实体）、DTO（入参传输实体）、VO（出参返回实体）、BO（业务实体），各实体职责单一，禁止跨层复用、万能实体；
2. 数据库实体：与数据表一一对应，字段严格匹配，仅包含数据库原生字段，不嵌套业务逻辑字段；
3. 数据转换规范：统一封装实体转换工具类，实现各层级实体互转，杜绝重复转换代码，遵循合成复用原则；
4. 数据访问控制：Mapper层仅负责数据库CRUD操作，无业务逻辑，SQL语句简洁高效，禁止复杂业务SQL嵌套数据层；
5. 字段管控：敏感字段（手机号、身份证、密码等）统一脱敏处理，禁止明文传输、明文存储；
6. 数据校验：入参非空、长度、格式、范围校验统一标准化，基础校验通用封装，业务特殊校验单独实现；
7. 缓存适配：高频查询数据合理配置缓存，缓存key统一规范，避免缓存穿透、击穿、过期问题。
8. 数据操作：尽量使用MybatisPlus进行数据库访问，当方法代码中出现多个数据库数据修改语句，则需要在方法添加事务注解。如果需要批量进行数据库操作时，不要使用循环发送的方式，而是编写一个xml文件，在其中写SQL，多表联查的SQL同样使用xml文件。如果进行删除数据的查询则需要使用原生的Mybatis的SQL操作方式，不能使用MybatisPlus查询已删除的数据信息。
9. 字段使用：所有新增、修改、删除数据库中的数据的SQL都不需要手动设置创建人ID、更新人ID、创建时间、更新时间，而是使用MybatisPlus中的拦截器进行统一填充

## 配置与属性
1. 配置分层：区分全局配置、业务配置、第三方组件配置，配置分类清晰，层级明确；
2. 环境隔离：严格区分开发、测试、预发、生产环境配置，各环境配置独立隔离，禁止环境配置混用、硬编码环境参数；
3. 配置规范：所有常量、自定义参数、第三方密钥、接口地址、超时时间等统一写入配置文件，禁止代码硬编码；
4. 配置读取：统一配置读取方式，封装通用配置读取工具，禁止零散读取、重复读取；
5. 动态配置：核心可变配置支持动态刷新，无需重启项目即可生效，适配业务动态调整；
6. 默认配置：所有自定义配置设置合理默认值，避免配置缺失导致项目启动异常；
7. 配置注释：所有配置项标注清晰注释，说明用途、取值范围、业务场景，方便维护迭代。
8. 代码注释：核心业务方法需要添加Java文档注解，如果有接口，直接在接口上写文档注解，而不是在实现类的方法上加，如果参数中有类，在注解中需要添加{@link 实体类}。添加单行注释时，不要添加序号，只针对于重要的代码进行注释。

## 异常处理
1. 异常分层规范：严格区分系统异常、业务自定义异常、未知异常，分层清晰、职责单一，禁止混用异常类型；自定义业务异常统一封装，用于业务校验、业务规则拦截，携带精准错误码与提示信息；系统异常用于框架、底层、工具类报错，统一全局兜底处理。
2. 全局异常拦截：项目必须配置全局异常处理器，统一拦截所有Controller层异常，集中处理、统一封装响应结果，杜绝分散式异常处理，遵循开闭原则，新增异常类型仅需拓展处理逻辑，不改动核心兜底代码。
3. 异常编码规范：统一全局错误码体系，分模块、分类型编码，错误码语义唯一、规则统一，搭配标准化提示文案，支持前端精准提示、问题快速定位。
4. 捕获与抛出规范：禁止滥用try-catch、禁止空catch块吞异常；精准捕获指定异常，不捕获最大父类异常笼统兜底；业务校验不通过优先抛自定义业务异常，而非返回错误码字符串，保证业务逻辑纯净。
5. 异常日志规范：业务异常打印精简日志，记录业务编号、报错场景；系统未知异常完整打印堆栈信息，便于排查问题；禁止打印敏感异常信息，禁止日志泄露账号、密码、手机号等隐私数据。
6. 兜底容错机制：所有外部调用、IO操作、第三方接口调用必须做异常容错，配置降级、兜底策略，避免单一点异常导致整体业务中断。
7. 拓展性规范：异常体系预留拓展能力，支持新增业务异常类、新增异常枚举（状态码、错误信息），适配业务迭代拓展需求，遵循合成复用原则，复用全局异常兜底能力。

## 日志与监控
1. 日志分级：严格区分ERROR、WARN、INFO、DEBUG日志级别，使用lombok的日志功能，不同场景使用对应级别日志，禁止滥用日志级别、冗余日志、无效日志；
2. 日志内容：日志打印关键参数、业务标识、操作链路、异常堆栈，日志信息完整精准，便于问题定位；
3. 日志规范：禁止打印明文敏感数据，日志格式统一，无乱打印、无重复打印；
4. 日志持久化：配置日志lombok日志配置文件，实现滚动策略、保留时长、文件大小限制，避免日志堆积占用资源；
5. 链路追踪：整合链路追踪工具，实现接口全链路日志追踪，适配分布式场景排查问题；
6. 监控体系：接入项目健康度监控、接口性能监控、异常次数监控、数据库监控、缓存监控；
7. 异常告警：核心业务异常、系统报错配置告警机制，及时发现并处理线上问题。

## 安全
1. 接口安全：接口防重放、防篡改、防暴力破解，统一请求鉴权、身份校验，未登录、无权限用户禁止访问核心接口；
2. 参数安全：拦截SQL注入、XSS跨站、特殊字符攻击，统一参数过滤、转义处理；
3. 权限安全：基于角色、资源、接口实现分级权限管控，权限粒度精细，杜绝越权操作；
4. 数据安全：敏感数据脱敏存储、脱敏传输，密码加密存储，禁止明文保存核心数据；
5. 依赖安全：定期排查项目依赖漏洞，升级高危依赖，杜绝第三方组件安全隐患；
6. 接口防刷：配置接口限流、熔断机制，防止恶意请求、高频请求击垮系统；
7. 运维安全：禁止暴露敏感配置、端口、路径，生产环境关闭调试模式，杜绝信息泄露。

## 性能与可扩展性
1. 代码性能：杜绝循环查询数据库、无效循环、冗余判断，精简代码逻辑，提升执行效率；
2. 据库性能：合理设计索引、避免慢SQL，分页查询、条件查询优化，禁止全表扫描，大表合理拆分；
3. 缓存优化：合理使用本地缓存、分布式缓存，控制缓存粒度，解决缓存穿透、击穿、雪崩问题；
4. 并发优化：核心接口适配并发场景，合理使用线程池、锁机制，避免并发冲突、数据脏读；
5. 可扩展性：架构无固化限制，支持业务模块新增、功能迭代、集群部署、分布式改造；
6. 兼容性：代码、配置、接口向下兼容，版本迭代不影响原有正常业务；
7. 资源管控：合理配置JVM参数、连接池参数、线程池参数，避免资源溢出、资源浪费。

## 构建与部署
1. 构建规范：统一Maven/Gradle打包配置，依赖版本统一管控，禁止版本冲突、冗余依赖，打包环境隔离；
2. 版本规范：项目版本迭代标准化，版本号语义化，迭代记录清晰，便于追溯；
3. 打包过滤：打包时过滤测试代码、本地配置、无效资源，精简包体大小；
4. 部署规范：区分多环境部署流程，部署步骤标准化、文档化，禁止随意部署、手动修改线上配置；
5. 自动化适配：支持CI/CD自动化构建、打包、部署，提升迭代效率；
6. 启动规范：统一项目启动参数、启动脚本，配置健康检查、优雅启停，避免暴力启停导致数据异常；
7. 回滚机制：支持版本快速回滚，部署失败可一键恢复，保障线上业务稳定运行。
