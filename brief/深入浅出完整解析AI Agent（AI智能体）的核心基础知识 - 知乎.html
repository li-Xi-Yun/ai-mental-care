过去我们和AI大模型交互，只能在一个典型的QA（Question-Answers）模式里：用户输入一个问题，AI大模型生成一个答案。这个过程可以很强，也可以很惊艳，但它本质上是“单轮生成”，整个过程是单次的、不可修改的。AI大模型不知道我们的真实工作环境，不能调用外部工具，不会天然保存长期上下文，也不会持续观察任务状态、修正执行路径、验证结果质量等操作。这就是经典的AI Non-Agent的工作流程：

而AI Agent要解决的，不只是AI大模型能否“回答得更好”，而是“能不能在真实环境里构建完成一个系统级项目、持续优化迭代内容、长期运营更新产品等”。Rocky认为，这可以说是AI/互联网行业研发模式革命级别的差别。

2. AI Agent的核心Agent Loop、上下文工程和设计模式零基础深入浅出理解

2.1 AI Agent的核心Agent Loop（代理循环机制）深入浅出理解

我们已经知道AI Agent的本质不是一次大模型调用，而是一个围绕大模型构建的可持续执行的AI系统。基于此，我们再往深思考一步，Rocky认为，其中Agent Loop（代理循环机制）就是AI Agent的最小生命结构。

所以Rocky认为我们学习AI Agent最先需要理解的就是Agent Loop的核心运行机制。

如果没有 Agent Loop，大模型只是一个问题回答器。它可以根据上下文生成文本，可以解释代码，可以给出建议，但它无法真正进入现实世界。因为它不知道文件是否真实存在，不知道测试是否真实通过，不知道命令是否执行成功，也不能把工具调用的结果带回到下一轮推理过程中。

而Agent Loop做的事情，就是把大模型从“生成答案”推进到“持续执行”：

大模型进行意图理解与分析，并提出下一步动作，其中可能包含工具执行等内容，最后完成的结果回到上下文，大模型继续判断是否还要行动。

这件事听起来简单，但它正是AI Agent从Chat形态跃迁到Agent形态的关键核心。

很多读者一开始学习AI Agent，看到复杂庞大的架构源码、工具调用、权限系统、上下文压缩、Hooks、Skills、MCP、RAG、Memory等模块，大概率会不知所措。但如果把这些复杂模块层层剥开，我们会发现最里面仍然是一个非常朴素的Agent Loop结构：只要任务还没有完成，就让大模型判断下一步；如果大模型需要外部工具的辅助，就执行工具并把真实结果写回上下文；如果大模型不再需要工具，就结束当前回合。

这时候可能有些读者会有疑问，为什么大模型为需要Agent Loop循环机制？Don't Worry，Rocky将会为大家娓娓道来。

因为单独的大模型本身并不能直接操作真实世界。它可以“说”应该读哪个文件，但它不能自己读文件；它可以“说”应该运行测试，但它不能自己运行测试；它可以“推测”bug 可能在哪里，但它无法验证这个推测是否成立。

在AI Non-Agent的式交互里，这个闭环是由人类补齐的：

1. 用户把问题发给大模型
2. 大模型给出建议
3. 用户手动复制命令去终端执行
4. 用户再把结果贴回大模型
5. 大模型继续分析

上述这种交互这当然也能执行工作，但效率非常低，而且上下文可以说是混乱无序。

而Agent Loop的本质，就是把这个“人工复制粘贴闭环”自动化和智能化。它让大模型不只是生成文本，而是能够在一个受控AI系统里持续工作：

1. 观察当前上下文
2. 推理下一步
3. 选择工具
4. 执行动作
5. 接收反馈
6. 更新状态
7. 判断任务是否完成

而这就是AI Agent的最小闭环，Rocky 认为，理解这一点非常重要。

因为很多关于AI Agent的讨论，一上来就堆概念：工具调用、上下文工程、Skills、Hooks、RAG、记忆、MCP、多 Agent、工作流等。但这些概念如果没有Agent Loop来进行串联，它们只是无价值的零件。Agent Loop才是把零件变成系统的那根核心主轴。下面是Rocky构建的Agent Loop精炼案例，大家可以结合代码深入浅出理解：

def agent_loop(query):
    # 1. messages是AI Agent的状态账本。
    # 用户最初的目标不是一次性prompt，而是整个循环的起点。
    messages = [{"role": "user", "content": query}]

    while True:
        # 2. 把当前完整状态交给大模型。
        # 大模型不是只看本轮输入，而是看 messages 里的历史、工具结果和系统约束。
        response = client.messages.create(
            model=MODEL,
            system=SYSTEM,
            messages=messages,
            tools=TOOLS,
            max_tokens=8000,
        )

        # 3. 大模型输出也要写回 messages。
        # 这样下一轮大模型才能知道自己刚才说过什么、计划过什么、调用过什么。
        messages.append({"role": "assistant", "content": response.content})

        # 4. 如果大模型没有请求工具调用，说明这一轮已经给出最终回答或阶段性结论。
        # 最小版本可以直接结束；实际AI Agent系统通常还会接 Stop Hook 或结果验收器。
        if response.stop_reason != "tool_use":
            return response

        results = []

        # 5. 遍历大模型返回的内容块，只执行其中的 tool_use。
        # 文本块负责解释，tool_use 块负责行动。
        for block in response.content:
            if block.type == "tool_use":
                # 6. 这里用 bash 举例。
                # 真实AI Agent系统必须在 run_bash 前加入权限检查、命令白名单、cwd 限制和审计日志。
                output = run_bash(block.input["command"])

                # 7. 工具结果必须带上 tool_use_id。
                # 这是把“大模型发起的工具调用”和“外部世界返回的结果”重新对齐的关键。
                results.append(
                    {
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": output,
                    }
                )

        # 8. 把工具结果作为 user message 写回 messages。
        # Agent Loop 的闭环就在这里完成：
        # LLM 产生行动意图，工具接触真实环境，结果再进入大模型的上下文。
        messages.append({"role": "user", "content": results})

我们如果只看Agent Loop的最小实现，其实并不复杂。它通常包含四件事：

  1. 一个消息列表 messages；
  2. 一次大模型调用 client.messages.create()；
  3. 一个工具执行器 dispatchTool()；
  4. 一个退出条件 stop_reason !== "tool_use"。

Rocky认为，我们可以把它理解成一条循环链路：

用户输入的问题进入 messages -> 调用 LLM -> 大模型返回 text 或 tool_use -> 如果是 tool_use 就执行工具 -> 工具结果作为 tool_result 加回 messages -> 再次调用 LLM -> 直到大模型不再请求工具。

这套逻辑非常像人类解决问题。比如让一个研发工程师修 bug，他会先看错误、查代码、改文件、跑测试、看失败日志、再改、再跑，直到测试通过。Agent Loop本质上做的也是这件事，只不过主角从人类工程师变成了AI大模型。因此AI Agent技术浪潮必定会迎来全面的AI/互联网行业研发范式革命与重构。

所以Rocky一直强调：AI Agent不是“AI大模型变得更聪明”这么简单，而是把大模型放进了一个可以行动、反馈、再行动的控制循环里的范式变化。

这也是为什么Rocky认为，AI Agent不是一个短期概念炒作，而是 AIGC 时代最具跨周期价值的方向之一。

AI大模型会继续变强，各种配套工具会继续变化，AI Agent框架也会不断迭代，今天流行的某些AI产品形态也可能被下一代大模型的基座能力直接吸收。但 “如何让AI Agent智能系统可靠地理解目标、连接环境、调用工具、保持状态、规划执行、反思修正、接受监督，并最终交付结果”，而这个伟大的AI Agent系统正是以这30行的Agent Loop代码为基石，逐步构建。

2.2 AI Agent的Prompt Engineering（System prompt、Assistant Prompt、User Prompt）核心基础知识

在AI Agent系统里，完整的Prompt体系不是几句“提示词咒语”，而是一套把大模型行为组织起来的“控制协议”。

很多读者把 System Prompt、Assistant Prompt、User Prompt 理解成三种文本格式，这是远远不够的。更准确地说，在AI Agent主流框架中，它们对应的是三层不同的控制面：

  • System Prompt（System Message）：它是 Agent 的“宪法层”，它定义模型身份、任务边界、安全策略、工具使用规则、输出格式、沟通风格、主动性边界，以及什么情况下必须请用户确认。
  • User Prompt（User Message）：它是AI Agent 的“目标层”，用户当前的问题、任务需求、业务背景、附件内容、代码片段、约束条件，通常都从这里进入系统。
  • Assistant Message（Assistant Message）：它是AI Agent 的“轨迹层”，代表大模型生成的内容，负责保留大模型已经做过什么、说过什么、调用过什么工具。

Rocky 认为，Prompt的本质不是“怎么把话说漂亮”，而是“怎么把意图、规则、历史和风险边界放到大模型能稳定理解的位置”。

一个典型AI Agent对话可以简单理解为：

System Message -> User Message -> Assistant Message -> Tool Result -> Assistant Message -> User Message …

其中最容易被误解的是 Assistant Message。

在普通Chatbot里，Assistant Message 看起来只是“上一轮回复”。但在 Agent 里，它往往还包含模型的行动意图。比如大模型决定调用文件读取工具、搜索工具、浏览器工具、Shell 工具，这些 tool_use 通常也是 Assistant Message 的一部分。工具执行结果再作为 tool_result 回到后续上下文里，大模型才能基于真实反馈继续决策。

所以，在AI Agent系统中，Assistant Message不是聊天记录，而是行动轨迹。

接下来，我们来理解System Prompt，是如何在AI Agent中生效的呢？

System Prompt的优先级通常高于用户输入（置于用户输入之前，在输入大模型文本序列的开端，由于注意力机制的特性：序列首尾信息通常更受关注，该位置的内容更容易被大模型识别和遵循），主要起到静默提示的作用，但这并不意味着它是万能防线。一个好的System Prompt不是把所有规则堆进去，而是在正确的抽象层级上写清楚：这个AI Agent 是谁、要解决什么问题、不能做什么、遇到不确定性如何处理、工具调用有什么边界、最终输出要满足什么标准。

同时，当前AI Agent系统有一个很重要的原则：System Prompt 要处在合适的“高度”。太低层，就会变成硬编码流程，脆弱、难维护；太高层，就会变成空泛口号，大模型不知道具体怎么做。真正好的 System Prompt，应该具体到足以约束行为，又抽象到能覆盖不同任务。

这也是Claude Code、Codex、Manus等AI Agent类产品共同体现出的趋势：Prompt 不再只是“角色设定”，而是越来越像一个轻量级操作手册。

一个工程化 System Prompt 往往包含以下模块：

  • 身份与目标：这个 Agent 的角色、服务对象和主要任务是什么。
  • 行为原则：主动性、谨慎性、是否允许推测、什么时候必须说明不确定性。
  • 工具策略：什么时候搜索，什么时候读文件，什么时候调用代码执行，什么时候禁止危险操作。
  • 输出契约：回答格式、引用要求、代码风格、语言风格、长度控制。
  • 安全边界：用户输入不可信、敏感信息不可泄露、高风险操作需要确认。
  • 示例与反例：用少量典型 good example / bad example 帮助模型区分相似但不同的行为。

在实际写法上，XML 标签和 Markdown 标题都很常见。比如用 <instructions>、<tool_policy>、<output_format>、## Tool guidance、## Tone and style 来划分模块。格式本身不是重点，重点是让模型看到清晰的边界。

对于User Prompt，我们则要从另一个角度理解。

User Prompt 是任务入口，但它也是风险入口。用户可能表达真实目标，也可能携带错误信息、模糊指令、提示词注入、恶意命令、提示词注入（Prompt Injection）等攻击手段，甚至把“忽略前面的系统规则”包装成普通需求。因此，AI Agent系统不能把User Prompt当成等价于开发者意图的最高指令。

更稳妥的做法是把User Prompt看成一个需要解析、校验和结构化的任务请求。

例如，一个成熟AI Agent 会从用户输入中拆出：

  • 用户真正想完成的目标；
  • 必须遵守的硬约束；
  • 可以推断但需要确认的隐含偏好；
  • 不可信、需要隔离处理的外部文本；
  • 需要工具或上下文检索才能验证的信息。

这也是为什么很多优秀 Agent 会引入类似 CLAUDE.md、AGENTS.md、agent.md、minusx.md 这样的上下文文件。

这类文件的价值，不是给大模型再写一段更长的 Prompt，而是把用户或团队的长期偏好沉淀下来：项目目录不要碰哪里、代码风格用什么、测试命令怎么跑、输出文风是什么、哪些操作必须先确认、哪些文件是核心上下文。

Rocky认为，CLAUDE.md 这类文件是 Prompt 工程走向上下文工程的过渡形态。它一方面仍然是文本指令，另一方面已经承担了“团队记忆”和“项目运行手册”的角色。

但这里也要注意一个边界：长期上下文文件不应该变成“垃圾桶”。凡是临时的、低信号的、会频繁变化的信息，不应该一股脑塞进这类文件。否则它会从“稳定偏好”变成“上下文污染源”。

最后，我们再把三类 Prompt 放在一起看，它们的关系可以总结为：

类型本质角色适合放什么不适合放什么
System Prompt规则层 / 宪法层身份、边界、工具策略、安全约束、输出契约频繁变化的业务数据、冗长知识库、用户临时偏好
User Prompt目标层 / 任务入口当前问题、当前约束、附件、用户期望未经校验就直接执行的危险命令
Assistant Message轨迹层 / 状态记录历史回答、行动计划、工具调用、错误痕迹伪造系统规则、不可追溯的隐式状态
Context File长期偏好 / 项目手册团队规范、项目结构、固定命令、长期风格短期日志、一次性搜索结果、无验证资料堆积

因此，Rocky认为Prompt 设计的长期价值不在于背某个模板，而在于理解不同信息应该放在什么位置。

如果把所有东西都塞进 User Prompt，Agent 会失去层级；如果把所有东西都写进 System Prompt，系统会变得僵硬；如果不保留 Assistant Message，Agent 就没有可追溯的行动轨迹；如果没有长期上下文文件，AI Agent又很难理解用户和项目的稳定偏好。

真正可用的AI Agent Prompt 系统，一定是分层的、结构化的、可调试的。

2.3 AI Agent的上下文工程（Context Engineering）核心基础知识

我们在理解了Prompt Engineering的核心基础知识后，再看Context Engineering，就会更加清楚和容易理解。

Prompt Engineering关注的是“怎么写好发给大模型的指令”。Context Engineering关注的是“在每一次大模型调用前，应该把哪些信息、工具、记忆、状态、历史和约束放进上下文窗口”。

Rocky 认为，上下文工程的本质，是在有限注意力预算里，为大模型搭建一个精炼但高信息量的工作台。

上下文工程不是把信息塞满，而是在每一轮Agent Loop 前重建最小高信号工作台。为什么这件事在 AI Agent 里突然变得重要？

因为AI Agent不再是一次性问答。它会循环，会调用工具，会读文件，会产生中间结果，会遇到错误，会修改计划，会跨几十轮甚至上百轮持续执行任务。每一轮都会产生新的状态，也会带来新的上下文污染。

长上下文当然重要，但长上下文不是免费午餐。上下文越长，大模型越容易遇到注意力稀释、信息干扰、长距离依赖变弱、重要信息淹没在中间位置等问题。Anthropic将这种现象称为context rot，Manus的工程经验也指出，真实AI Agent的输入输出token比例会远高于普通Chatbot，很多时候大模型每一轮都在消化很长的历史，却只输出一个很短的工具调用。

所以，Context Engineering不是“把更多东西塞进上下文窗口”，而是回答解决很多更难的核心工程问题：

在当前这一步，哪些 token 最值得大模型注意？哪些信息必须保留？哪些信息应该外部化？哪些历史可以压缩？哪些错误必须留下？哪些工具应该可见？

上述举例的这些问题一旦处理不好，AI Agent 就会出现很多熟悉的问题：越跑越慢、越跑越贵、越跑越偏、重复犯错、忘记目标、误用工具、把低价值历史当成重要证据。

因此，一个成熟的上下文工程系统，至少要处理七类信息：

  • 稳定指令：System Prompt、工具规则、安全边界、输出契约。
  • 用户目标：当前任务、显式约束、隐含偏好、交付标准。
  • 消息历史：多轮对话、模型回答、行动计划、工具调用记录。
  • 环境反馈：工具结果、错误信息、文件变化、网页内容、数据库查询结果。
  • 外部记忆：CLAUDE.md、AGENTS.md、NOTES.md、todo.md、长期记忆数据库等。
  • 检索内容：RAG 结果、代码搜索结果、文件路径、链接、SQL 查询结果。
  • 运行状态：当前轮数、token 预算、权限状态、是否压缩过、是否需要人工确认。

Rocky认为可以把这些信息分成三层：

【第一层是稳定前缀】

稳定前缀包括 System Prompt、工具 schema、基础安全策略和固定输出契约。它最好尽量稳定，因为在推理系统里，前缀稳定意味着更好的缓存命中、更低延迟、更低成本，也意味着大模型每一轮看到的规则更一致

Manus的一个重要经验是围绕 KV-cache 设计上下文。Agent 的上下文通常不断增长，但前面的大量内容是重复的。如果每轮都改变系统提示、工具定义或序列化顺序，就会破坏缓存，也会让大模型看到不稳定的行为边界。

这给工程上的启发很直接：不要把每秒变化的时间戳、随机排序的 JSON、临时业务数据放在系统前缀里；工具定义不要频繁增删；消息序列尽量 append-only；序列化要确定性。

【第二层是动态工作区】

动态工作区是每一轮大模型调用前真正需要调度的部分。它包括当前任务、最近对话、必要工具结果、检索片段、当前计划、错误信息和下一步约束。

这里的核心不是“多”，而是“准”。好的上下文工程要追求最小高信号 token 集合：足够让模型做出正确下一步，但不把无关网页全文、重复日志、过时计划、低质量检索结果全部塞进去。

这也是 just-in-time context 的价值。对于大文件、大数据库、大网页，不一定要提前全部放进上下文。更好的方式是保留文件路径、SQL 查询、URL、索引、摘要和元信息，让 Agent 在需要时通过工具逐步读取。

这和人类工作很像：我们不会把一本书的所有内容背下来，而是记住目录、书签、文件名和检索方式，需要时再翻到关键页。

【第三层是外部化记忆】

真正长周期的AI Agent不能只依赖上下文窗口。无论上下文窗口有128K、1M还是更大，只要任务足够长，窗口都会变成瓶颈。

所以，文件系统、笔记、todo 列表、长期记忆数据库，会成为AI Agent的外部大脑。Manus把文件系统视为最终上下文，Claude Code会依赖项目文件、最近访问文件和压缩摘要，MinusX也把 minusx.md 作为记录用户和团队偏好的上下文文件。

Rocky认为，这背后有一个非常关键的核心原则：

能外部化的长期状态，不要长期压在大模型上下文窗口里；能通过工具恢复的信息，不要不可逆地压缩成一句话。

总的来说，Rocky认为正如Andrej Karpathy所指出，我们可以将LLM/AIGC大模型理解为一种全新的计算机操作系统——LLM/AIGC大模型本身相当于“CPU”，而其上下文窗口则类似于“RAM”，承担着工作记忆的功能。与物理内存的容量限制类似，上下文窗口所能容纳的信息量也有限。因此，“上下文工程”的核心职责，正如操作系统对内存的调度管理，是在有限的上下文窗口内，科学、高效地组织信息，以支持模型完成当前任务。

Karpathy 对此作出了精辟总结：

“在每一个具备工业级规模的AI Agent系统中，上下文工程都是一门融合了艺术性与科学性的精细技艺，其关键在于为下一步任务精准配置上下文窗口中的信息内容。”

这一演进背后的根本动因在于，当前LLM/AIGC大模型的能力虽持续进步，但仍未达到无需工程辅助即可解决所有复杂问题的水平。因此，上下文工程在现阶段成为必要手段。未来，随着大模型能力的进一步跃升，相应的工程范式也可能继续动态演变。

最后Rocky再向大家分享上下文工程中有七个非常重要、具备跨周期价值的实践原则。

第一，稳定前缀，追加历史。

System Prompt、工具定义、基础策略尽量稳定；历史记录尽量追加，不要反复改写过去的 action 和 observation。这样既有利于缓存，也有利于可追溯。

第二，工具不是越多越好。

工具定义会占用上下文，也会扩大模型的 action space。工具过多，大模型反而更容易选错。Manus 提到一个很有启发性的做法：不要频繁移除工具定义，而是用状态机、工具可用性和响应预填充等方式限制当前可选动作。简单说，就是“mask，不要乱删”。

第三，用文件系统和引用代替全文堆叠。

对于网页、PDF、代码库、数据库结果，很多时候应该保留可恢复引用，而不是把所有原文都塞进去。文件路径、URL、查询语句、摘要、最近访问记录，都是高价值上下文。

第四，让AI Agent反复重述目标。

长任务里，AI Agent很容易跑偏。todo.md、计划列表、阶段目标、验收清单，本质上都是把全局目标重新放回大模型的近端注意力范围。Manus 把这种机制称为 recitation，Claude Code 式 Todo List 也是类似思想。

第五，不要把错误痕迹全删掉。

很多AI Agent系统一看到工具失败就清理日志、重试、假装没发生过。但对AI Agent来说，错误是非常重要的反馈。失败命令、报错栈、权限拒绝、无效搜索结果，都可能帮助大模型下一轮避开同样的坑。

真正好的AI Agent不是从不犯错，而是犯错之后能把错误变成高价值的上下文。

第六，压缩要可恢复。

Compaction是长任务必须面对的机制，但压缩不是随便总结。好的压缩要保留决策、约束、未解决问题、关键文件、失败原因和下一步计划；删除的应该是重复工具输出、冗余对话和低价值噪声。

过度压缩会让AI Agent失忆；不压缩会让AI Agent被噪声淹没。上下文工程的难点就在这里：不是压缩越狠越好，而是要考虑到召回率和精确率之间的平衡。

第七，避免把AI Agent few-shot到固定套路里。

少样本示例很有用，但在 Agent Loop 里，大量相似 action-observation 对会让大模型模仿历史模式，即使当前任务已经变化。上下文太整齐、太重复，有时反而会让AI Agent 进入惯性路径。

因此，示例要少而精，最好覆盖真正关键的分叉点，而不是堆很多相似案例。

把这些原则合在一起，我们可以得到一个更实用的判断框架：

问题低质量做法高质量上下文工程做法
任务背景很多全部塞进 prompt保留摘要、路径、索引，需要时再读取
工具很多动态增删工具列表保持工具定义稳定，用状态约束当前可用工具
长任务跑偏继续堆历史维护 todo / plan / 验收清单，把目标放回近端上下文
工具失败清理痕迹后重试保留错误，结构化失败原因，让模型恢复
上下文快满粗暴截断高召回压缩，保留决策、约束、未完成事项和恢复引用
需要外部知识一次性 RAG 塞满预检索 + 运行时自主搜索的混合策略

可以看到，上下文工程它是AI Agent的运行时信息核心调度系统。

Prompt 工程解决的是“怎么对大模型下指令”；上下文工程解决的是“大模型每一步应该看见什么”。前者更像写说明书，后者更像操作系统管理内存、文件、缓存、进程状态和异常恢复。

Rocky最后给一个本质判断：未来大模型会更强，长上下文会更大，工具协议会更标准，但上下文工程不会消失。因为只要AI Agent 要跨多轮行动、跨工具执行、跨文件工作、跨时间保持目标，它就必须管理有限注意力、外部记忆、工具反馈和失败恢复。

上下文工程的长期价值，不在于某个具体框架，而在于它抓住了AI Agent系统最底层的问题：智能不是一次性生成，而是在有限信息中持续选择、行动和修正。

【综合案例：AI客服助手】

场景描述：用户Alice的笔记本电脑无法开机，联系”量子科技商城”客服要求退货。

完整的上下文结构包含多个协同工作的组件：

2.4 AI Agent的主流设计&工作模式

Rocky认为，当前主流的AI Agent（Codex、Claude Code、Cursor、OpenClaw、Manus等）的设计思想，并不是几种彼此孤立的架构，而是把大模型放进一个可执行、可观测、可恢复、可交付的 runtime 里。

从AI Agent的设计工程视角看，大模型负责决策，整体系统负责边界、状态和交付。大模型负责下一步想什么，系统负责什么时候停、什么时候询问用户、什么时候验证、什么时候回滚。这个分工一旦成立，AI Agent才真正从“问答”走向“执行”。

AI Agent的主流模式不是互斥关系，而是同一条链路上的不同控制点。

AI Agent 里常说的 Reflection、Tool use、ReAct、Planning、多智能体，本质上不是一堆互相替代的概念，而是围绕同一个问题展开的不同解法：任务怎么进入、上下文怎么组装、动作怎么发出、结果怎么观察、失败怎么恢复。

真正成熟的AI Agent，一定不是只押一个模式，而是把这些模式组合成一个分层系统：

  1. 低层做局部循环，解决“怎么做下一步”。
  2. 中层做任务规划，解决“先做什么、后做什么”。
  3. 高层做工作流、权限和审批，解决“哪些事能自动做，哪些事必须确认”。
  4. 更外层再叠加多智能体协作，解决“如何并行、分工和交接”。

所以，AI Agent设计的核心，不是某个单点技巧，而是将不同模式如何更好的的组合与协同应用。

模式解决的问题核心机制常见失败方式跨周期价值
Reflection先做完再做对自检、批评、修正只会“自我循环”，没有客观评价把一次性生成变成可迭代生成
Tool use让大模型接触外部世界结构化调用、观察回传工具选错、参数错、结果不校验把大模型从知识体变成行动体
ReAct不确定环境下的在线决策Thought-Act-Observation 交织步数变多、状态漂移、越想越慢最通用的在线 Agent 循环
Planning长任务的分解与调度目标拆解、阶段检查、重规划计划写得很漂亮，执行跟不上把复杂任务变成可管理任务
Workflow / Graph业务流程的稳定落地状态机、图编排、分支控制灵活性下降、设计成本上升最接近企业级基础设施
Multi-agent复杂任务的分工与并行角色划分、委派、汇总协调成本高、信息不一致把“个人智能”推向“组织智能”

基于上面的框架，形成了下面的5种主流AI Agent设计模式：

【反射模式（Reflection Pattern）】

在AI Agent系统中，Reflection Pattern被定义为一套让AI Agent对自身或其他Agent的推理过程、行动计划或生成结果进行批判性审视与评估，从而发现错误、不足并实现自我改进的技术框架。其核心是引入一个独立的“反思循环”，将单一的推理生成过程，升级为一个“生成-评估-改进”的迭代闭环，其中的核心是构建一个双Agent系统，Rocky认为其本质在于它把推理输出和结果评估拆开了。

AI Agent会审查工作过程，大模型先生成，再由另一个视角去审查、批评、修正。这个结构在写作、代码、方案、推理题里都很有用，因为它解决的是人和大模型都容易犯的一个老问题：第一版结果往往能跑，但未必稳定可靠。

Rocky认为，Reflection Pattern之所以长期有价值，是因为它把“生成”变成了“可修正的生成”，这对AI Agent特别重要。AI Agent不是只生成一次答案就结束，它要面对真实环境里的缺漏、冲突和错误，所以必须允许自己被纠错。

但Reflection Pattern也有明显边界：如果没有客观评价标准，它很容易退化成自说自话。真正有用的反思，不是“我觉得我已经不错了”，而是“我能不能拿测试、规则、约束、审查结果来证伪自己”。所以 Reflection Pattern最适合和测试、评审器、规则检查器一起用。

Rocky接下来以代码的生成与优化为例，构建的一个通用的Reflection Pattern代码框架，向大家详细讲解其核心机制的工作流程：

import openai

# 定义一个主执行Agent（例如程序员）
def actor_agent(task_description, feedback=None):
    system_prompt = "你是一名专业的程序员。请根据任务描述和反馈编写高质量的代码。"
    if feedback:
        user_content = f"任务: {task_description}\n之前的反馈: {feedback}\n请根据以上反馈改进你的代码。"
    else:
        user_content = f"任务: {task_description}\n请开始编写代码。"

    # 调用LLM生成代码
    response = openai.chat.completions.create(
        model="gpt-5.1",
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_content}
        ]
    )
    return response.choices[0].message.content

# 定义一个反思Agent（例如审查员）
def reflection_agent(task_description, actor_output):
    system_prompt = "你是一名严格的代码审查员。你的目标是发现代码中的错误、低效之处和潜在风险，并提供具体的改进建议。"
    user_content = f"审查以下代码：\n任务描述: {task_description}\n生成的代码: {actor_output}"

    # 调用LLM进行反思
    response = openai.chat.completions.create(
        model="gpt-5.1",
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_content}
        ]
    )
    return response.choices[0].message.content

# 主循环：Reflection Process
def reflection_loop(task, max_iterations=3):
    current_output = None
    feedback = None

    for i in range(max_iterations):
        print(f"--- 第 {i+1} 轮迭代 ---")
        # 1. 执行者生成输出
        current_output = actor_agent(task, feedback)
        print(f"【执行者输出】:\n{current_output}")

        # 2. 反思者进行评估
        feedback = reflection_agent(task, current_output)
        print(f"【反思者反馈】:\n{feedback}")

        # 3. 简单判断：如果反思者认为“无需修改”，则提前结束
        if "无需修改" in feedback or "代码良好" in feedback:
            print("反思完成，结果满意。")
            break
    else:
        print(f"已达到最大迭代次数 {max_iterations}。")

    return current_output

# 使用示例
if __name__ == "__main__":
    coding_task = "编写一个Python函数，计算斐波那契数列的第n项。"
    final_code = reflection_loop(coding_task)

# 代码框架解读：
# 角色分离：主执行Agent 和 reflection_agent 是两个独立的函数，拥有不同的系统提示（System Prompt），模拟了不同的角色。
# 反馈循环：reflection_loop 函数实现了核心循环。在每一轮中，执行者根据任务和上一轮的反馈生成输出，然后反思者对该输出进行批判性评估，生成新的反馈。
# 迭代终止：循环设有最大迭代次数，防止无限循环。同时，可以基于反思者的反馈（例如，当反馈认为“代码已完美”）来提前终止，提升效率。

通过这种架构，AI Agent不再是“一次性”地生成答案，而是具备了自我质疑、自我改进的能力，这正是其迈向AGI的关键一招。

【工具使用模式（Tool Use Pattern）】

AI Agent系统允许LLM/AIGC大模型通过使用外部工具获得更多信息，包括调用API、使用各种配套AI服务、查询矢量数据库、执行代码脚本等。这使得LLM/AIGC大模型不仅仅依赖于其内部知识，开始和外部世界发生真实交互。搜索、检索、代码执行、文件系统、浏览器、API、数据库、计算器，这些工具共同构成了大模型的“感知”和“动作”接口。

Tool Use（工具调用） 的通俗比喻，确实如同一个人使用计算器解决复杂算术问题。在AI Agent系统中本质上则是赋予LLM/AIGC大模型与环境交互并执行具体操作的能力。

以Codex类AI Agent系统为例，文件系统、终端、测试、补丁、日志、审批，本质上就是工具层和执行层。大模型在上层负责判断“下一步要做什么”，工具层在下层负责把这个判断变成真实状态变化。没有工具层，模型只能说；有了工具层，模型才开始做。

这标志着LLM大模型从一个封闭的、基于静态知识的生成式黑盒，向一个开放的、能够采取行动的问题解决者的根本性转变。大模型不再仅仅“说出”它认为的答案，而是能够“动手”去获取、计算和验证答案。

工具调用的过程可以分解为一个清晰的逻辑链条，具体来说，上图中的每一步都对应着以下技术细节：

  • 意图理解与工具选择：当大模型接收到一个用户输入时，它会先推理从而对输入进行意图理解，判断是否需要以及需要调用哪些工具。这里我们通常先给大模型一个可选工具的清单文件，其中包含对各种工具功能的“理解”。比如每个工具的名称、描述和参数格式。大模型会将自己匹配使用合适的工具。
  • 结构化调用：大模型不会随意地“说出”要调用的外部工具，而是会生成一个结构化的调用请求（例如符合特定JSON/XML格式的请求）。这确保了AI Agent系统中其他的配套代码服务能够准确解析调用请求并执行。例如，对于计算请求，大模型可能输出：{"tool": "calculator", "action": "evaluate", "input": "12345 * 67890"}。
  • 结果整合与输出：大模型接收到工具的返回结果（如上例中的 "838102050"）后，会将其作为新的事实依据，融入到最终的自然语言的回答中。例如：“12345 乘以 67890 的结果是 83亿8千1百零2万零5百（83,810,20,500）。”

外部工具的引入极大地扩展了大模型的能力边界，其类型也是多种多样：

  • 检索类工具：搜索引擎、知识库/向量数据库查询，用于获取实时、精准、私有的信息。
  • 计算与数据处理类工具：计算器、代码执行环境（如Python）、API数据获取，用于完成精确计算和逻辑处理。
  • 操作类工具：发送邮件、操作日历、控制智能家居，让模型能够影响物理世界。
  • 专业领域工具：如法律案例检索、医学文献分析、金融数据分析等垂直领域的专业工具。

但工具使用也有一个很现实的风险：工具越多，幻觉不一定越少，反而可能因为选择空间变大而更容易走偏。所以Rocky认为真正重要的不是“接了多少工具”，而是有没有清晰的工具协议、权限边界和结果校验。

下面是Rocky构建实现的AI Agent工具调用示例，让大家更好的学习领悟AI Agent调用外部工具的整个流程：

import openai
import json
import requests

# 1. 定义我们可供调用的工具列表
def get_current_temperature(city: str) -> str:
    """根据城市名获取当前温度。这是一个模拟函数。"""
    # 这里本应调用真实的天气API，例如OpenWeatherMap
    print(f"[系统日志] 正在查询{city}的天气...")
    # 模拟返回数据
    mock_data = {"city": city, "temperature": "22", "unit": "摄氏度"}
    return f"{mock_data['city']}当前的温度是 {mock_data['temperature']} {mock_data['unit']}。"

# 将我们的函数描述成模型可以理解的形式
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_current_temperature",
            "description": "获取指定城市的当前温度",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {
                        "type": "string",
                        "description": "城市名称，例如：北京，上海",
                    }
                },
                "required": ["city"],
            },
        },
    }
]

# 2. 与模型对话，并让它决定是否调用工具
def run_conversation(user_input):
    # 第一轮：将用户输入和工具描述发送给模型
    response = openai.chat.completions.create(
        model="gpt-5.1",
        messages=[{"role": "user", "content": user_input}],
        tools=tools,
        tool_choice="auto", # 让模型自动决定是否调用工具
    )
    
    message = response.choices[0].message
    print(f"【模型初始回复】: {message}")

    # 3. 检查模型是否想要调用工具
    if message.tool_calls:
        # 模型请求调用工具
        print("【模型决定调用工具】")
        # 可能存在多个工具调用，这里处理第一个
        tool_call = message.tool_calls[0]
        function_name = tool_call.function.name
        function_args = json.loads(tool_call.function.arguments)

        # 4. 在代码中执行被请求的函数
        if function_name == "get_current_temperature":
            city = function_args.get("city")
            function_response = get_current_temperature(city)
            print(f"【工具执行结果】: {function_response}")

        # 5. 将工具返回的结果作为新消息发送给模型，让它来总结
        second_response = openai.chat.completions.create(
            model="gpt-5.1",
            messages=[
                {"role": "user", "content": user_input},
                message, # 模型的第一次回复（包含工具调用请求）
                {
                    "role": "tool",
                    "tool_call_id": tool_call.id,
                    "content": function_response, # 工具的执行结果
                },
            ],
        )
        return second_response.choices[0].message.content
    else:
        # 模型没有调用工具，直接返回其回答
        return message.content

# 运行示例
if __name__ == "__main__":
    user_question = "请问北京现在多少度？"
    final_answer = run_conversation(user_question)
    print(f"\n【最终回答】: {final_answer}")

# 代码逻辑解读：
# 工具定义：我们定义了一个真实的Python函数 get_current_temperature，并用模型能理解的JSON格式描述了它。
# 模型决策：我们将用户问题和工具列表一起发给模型。模型会推理出“北京的温度”需要调用天气工具，于是它返回了一个结构化的工具调用请求，而不是直接编造一个温度。
# 本地执行：我们的代码解析这个请求，并实际执行对应的本地函数（这里模拟了API调用）。
# 结果整合：我们将工具执行的结果（“北京当前的温度是22摄氏度”）作为新的上下文送回给模型。模型利用这个确凿的事实，组织成一句流畅的自然语言回复给用户。

通过这种方式，AI Agent系统变成了一个“善于利用各种专业工具的团队协调者”，其能力和可靠性都得到了质的飞跃。

【ReAct模式（Reason and Act Pattern）】

ReAct模式结合了反射模式和工具使用模式，这使其成为AI Agent系统使用的最主流模式之一。AI Agent既可以自我思考，自我纠错，还可以使用工具与世界交互。它的核心不是先想完再做，而是边想边做、边做边看结果，然后再决定下一步。这个模式在信息不完整、环境状态会变化、任务路径不确定的时候特别有用。

它的优势很直接：不需要一次性把所有计划都写死，也不需要大模型把所有答案都“预知”出来。它只需要在每一轮做一个相对合理的局部决定，然后根据环境反馈继续推进。这也是为什么 ReAct 在检索、问答、调试、数据探索和轻量任务执行里都很常见。

不过，ReAct模式也有典型缺点：如果任务太长，它可能会陷入局部最优；如果上下文管理不好，它会重复走回头路；如果没有终止条件，它会一直陷入低效的循环迭代。ReAct模式适合做在线循环，但不适合单独承担长周期项目的总控。

【规划模式（Planning Pattern）】

在这种模式下，AI Agent根据任务的复杂程度，设计任务计划流程，对任务进行细分，再对细分子任务动用ReAct模式进行处理。可以说这种模式是一种AI Agent系统级别的战略思维，可以更有效地解决战略级复杂任务。

Planning模型的本质，是把模糊任务目标拆成一串可执行子任务，并给每一段任务加上阶段检查。很多人以为规划只是列清单，但真正有效的规划其实是状态管理：当前做到哪一步、还缺什么信息、下一步应该调用什么工具、哪个步骤需要重试。这也是为什么复杂任务里，规划比“即时反应”更重要。

Rocky更愿意把 Planning模式看成一种“可压缩的未来”。它不是承诺，而是给AI Agent执行提供方向。计划本身不是终点，计划被执行、被修正、被回写，才真正形成价值。

这就像一位项目负责人接到“举办一场产品发布会”的指令后，他不会立刻去搭建舞台，而是会先制定一个详尽的计划：市场调研 -> 确定主题 -> 邀请嘉宾 -> 撰写讲稿 -> 场地布置 -> 现场执行。这个制定计划的过程就是“规划”，而为每个步骤做出决策（例如选择哪位嘉宾、讲稿重点是什么）的思考过程就是“推理”。

在AI Agent中，Planning模式本质是让AI大模型从“刺激-反应”的模式，升级到“目标-规划-行动”的高级认知模式：

  • 任务分解：将模糊、复杂的用户指令（如“帮我做一份竞品分析”）转化为清晰、具体的子任务链（如“1. 确定竞争对手 -> 2. 爬取产品信息 -> 3. 对比功能特性 -> 4. 生成分析报告”）。
  • 状态管理：在整个过程中，AI Agent需要维护一个“任务状态”，明确当前进度、已获得的信息以及下一步需要做什么。
  • 工具编排：规划的核心作用之一就是智能地调用工具。它决定在什么时间、以什么顺序、使用哪些工具，并将上一个工具的输出作为下一个工具的输入，形成高效的工作流程闭环。

上述讲到的流程主要是线性规划（Sequential Planning），是最简洁的一种。在实际应用中，还有更复杂的动态规划、并行规划等范式。

【多智能体模式（Multi-Agent Pattern）】

在这个模式中，AI Agent系统中包含多个子Agent，每个子Agent都分配有一个专用的角色和任务，同时每个子Agent还可以访问外部工具进行综合工作。最后，所有子Agent协同工作以提供最终结果，同时根据需要将细分任务委派给其他子Agent，形成一个复杂的“AI Agent协同社区”。

多智能体模式的直觉很简单：让多个具备自主决策能力的AI智能体通过沟通、协调与配合，去共同完成一个复杂任务，像一个小团队那样分工。有人负责规划，有人负责检索，有人负责写代码，有人负责审查，有人负责汇总。一个智能体可能只擅长某个特定领域，但当多个各怀绝技的智能体组成团队时，就能解决远超单个智能体能力范围的复杂问题。它能带来并行能力，也能带来角色专精，这背后透露出精炼核心成员团结力量大的本质逻辑。

但Rock认为，多智能体真正难的，从来不是“把名字分开”，而是“把责任、状态和共识建立起来”。没有共享状态，没有清晰委派，没有统一验收口径，多智能体就会变成多轮互相打断、多次重复解释、最后谁都不完全负责。

要实现有效协作，智能体们需要一套稳定高效的运作机制。在实际应用中，多智能体系统演化出了多种协作模式，适用于不同的场景：

模式运作方式适用场景
工作流模式智能体像流水线一样按固定顺序依次工作，前一个的输出是后一个的输入。软件开发、多步骤推理管道。
路由模式一个“路由器”智能体根据任务内容，将其动态分配给最合适的专业智能体处理。客服系统、需要动态决策的场景。
层级模式类似公司层级，顶层“经理”智能体负责规划和分发任务，并管理底层“员工”智能体。复杂任务规划、需要全局协调的项目。
聚合模式让多个智能体对同一问题给出方案，再由一个主智能体汇总提炼出最佳答案。需要集思广益或进行质量评估的场景，如投票系统。

我们以 Codex 为例，它最像的并不是一个单纯的聊天模型，而是一个围绕任务执行搭建起来的运行时。大致会经历这样一条链路：

1. 用户提出任务，系统先判断目标、约束和可用边界。
2. 上下文被重新组装，相关文件、历史信息、规则和技能被放到一起。
3. 模型开始规划下一步，是先看文件、先搜信息，还是先调用工具。
4. 工具层执行动作，例如读取文件、修改代码、跑测试、检查结果。
5. 系统接收观察结果，判断是继续推进、重新规划，还是回滚修正。
6. 关键操作触发验证和审批，避免模型越权或者错误扩散。
7. 最后输出的是一个可交付结果，而不是一段看起来很聪明的回答。

2.5 AI Agent的上下文压缩与中断恢复

很多AI Agent都能顺利完成前几轮：大模型拆解任务，调用工具，构建项目，然后给出一个看起来不错的结果。但只要任务从十分钟拉长到几个小时，甚至跨天、跨设备执行，有两个重要的问题就会迅速暴露：

  1. 上下文负荷过载：对话、文件和工具结果越积越多，上下文窗口开始容纳不下。
  2. 运行波动中断：网络、进程、模型 API、终端任务的波动或用户操作随时可能打断 Agent Loop。

第一个问题要求AI Agent 学会“忘记”，第二个问题要求AI Agent 学会“想起来之后继续工作”。看起来是两个问题，Rocky认为实际上它们共享同一个底层命题：如何在记忆不完整、进程不可靠、外部世界继续变化的情况下，保持任务语义与执行结果的连续与正确。

Rocky认为，这是 AI Agent 从“一次性演示”走向“可交付系统”的分水岭。大模型强大的基座能力，决定了AI Agent单次推理能走多远；而上下文压缩与中断恢复的强鲁棒性，才决定了它跌倒以后能不能回到正确的路上。

我们先对一个常见误区进行解释：上下文压缩不是简单的“把历史对话写短”。对一个聊天机器人来说，压缩可能只需要记住“用户喜欢什么、刚才聊了什么”。但对AI Agent 来说，压缩的对象不只是文本信息，还包括正在执行的任务状态：

  • 用户真正的目标与验收标准是什么。
  • 已经做了哪些决策，为什么这样决策。
  • 哪些文件被读取或修改，当前版本是什么。
  • 哪些工具已调用，哪些调用有副作用。
  • 哪些错误已经发生，哪些路径被证明不可行。
  • 哪些任务已完成，哪些任务待办，当前正停在哪一步。
  • 权限、安全边界、人工审批和项目预算是否发生变化。

因此，压缩后的上下文不应该只有一段散文摘要，而应该像一个“继任者交接包”：下一个大模型实例即使没有看过原始对话，也能知道任务从哪里开始、已经发生了什么、当前处在什么状态、下一步应该做什么。

从形式上看，一次成熟的上下文压缩重建可以表示为：

C_{t+1}=S_{\text{stable}}+M(H_{\text{old}})+H_{\text{recent}}+W_{\text{active}}+R_{\text{external}}+P_{\text{runtime}}

其中，S_{\text{stable}} 是稳定指令与安全规则，M(H_{\text{old}}) 是旧历史的语义压缩，H_{\text{recent}} 是保留原文的最近工作集，W_{\text{active}} 是当前计划与未完成任务，R_{\text{external}} 是文件、日志、数据库和其他可恢复引用，P_{\text{runtime}} 则是工具、权限、审批和执行预算。

这个式子背后有一个非常重要的本质判断：摘要只是压缩产物的一部分，不是全部。我们需要构建完整的压缩后上下文工程，来让AI Agent进行自然的衔接与继承。

上下文压缩过程中要避免的不是“少记一句话”，而是丢失因果关系。上下文压缩的目标不是追求最高压缩率，而是在 Token 预算内最大化任务可继续性：

C^*=\arg\max_{C'}\left[U_{\text{task}}(C')+\lambda U_{\text{recovery}}(C')-\mu\,\operatorname{Tokens}(C')-\nu\,\operatorname{Drift}(C')\right]

这里的 U_{\text{task}} 表示对当前任务的有用性，U_{\text{recovery}} 表示能否支持恢复，\operatorname{Tokens} 是推理成本，\operatorname{Drift} 则是压缩造成的目标偏移。

一个效果差的压缩策略，通常会造成五种信息损失：

损失类型典型表现实际后果
语义损失忘记用户明确约束、验收标准交付物看似完成，实际答非所问
因果损失只记录“选了 A”，不记录“为什么放弃 B”恢复后重新走一遍已失败路径
引用损失丢失文件路径、任务 ID、工具调用与结果配对无法找回原始证据，甚至产生非法 API 消息序列
操作损失忘记哪些外部动作已发出重复发布、重复扣款、重复修改文件
安全损失忘记权限拒绝、人工审批和风险约束恢复后在错误边界上继续执行

因此，上下文压缩并不是一个纯NLP摘要问题，它还是数据结构与一致性问题。比如在Tool Use任务中tool_use和tool_result必须成对保留，很多文字上看起来很完整的摘要，不代表它在协议层仍然是一个合法的AI Agent状态。

Rocky认为，成熟的上下文压缩不是一把剪刀，而是一套分层存储。一个跨周期的AI Agent上下文系统，至少应该有五层压缩策略：

  1. 第一层：结构清理，不改变任务语义。优先删除重复的工具输出、重复注入的说明、过期的进度通知和可从原文重新获取的媒体内容。这一层最接近无损压缩，应该最先发生。
  2. 第二层：微压缩（Micro-compaction），清理“大但可恢复”的观察。工具结果往往是AI Agent上下文中最大的部分。对旧网页全文、过时搜索结果、已处理日志、超长命令输出，可以保留工具 ID、参数、短摘要与外部引用，将原始大块内容移出活跃窗口。
  3. 第三层：语义压缩（Semantic compaction），把旧历史改写成结构化交接包。应优先保留用户目标、硬约束、关键决策、文件变更、失败与修复、未完成任务、当前工作以及下一步，而不是追求语句的流畅缩写。
  4. 第四层：保留近端原文（Recent raw tail），不要将全部内容都简化成摘要。最近几轮消息、当前工具交互和尚未闭合的因果链应保留原文。摘要提供全局地图，近端原文提供局部精度，两者缺一不可。
  5. 第五层：状态外部化与重水化（Rehydration）。计划文件、Todo、已调用 Skill、最近读取文件、工具定义、MCP 说明、权限状态和运行时Hooks等不应只寄希望于在归纳的摘要中被“顺手记住”。它们应该拥有独立状态，在压缩后按需重新注入。

讲完了AI Agent系统的上下文压缩工程，Rocky再带着大家详细讲解AI Agent系统中常出现的终端恢复策略。

【中断恢复的第一步：不是“继续”，而是先判断刚才到底发生了什么】

上下文压缩发生在Session会话仍然存续时，中断恢复则面对一个更麻烦的问题：内存中的 runtime 状态可能已经消失，同时外部世界可能已经被改变。

一次工具调用在逻辑上可以经历以下状态：

PLANNED → DISPATCHED → SUCCEEDED / FAILED
                       ↘ UNKNOWN

UNKNOWN 是恢复系统里最危险的状态。它表示AI Agent 已经发出动作，但在拿到或持久化确认之前中断。例如：

  • 请求可能还没有到达服务器。
  • 请求可能已经完成，但响应在返回前丢失。
  • 文件可能只写入了一部分。
  • 命令可能仍在后台运行。
  • 子Agent可能已经产生结果，但主控Agent还没有汇总。

如果重启后不做判断，只是向大模型发一句“Continue from where you left off”，就可能把一次正常完成的操作重复执行。所以成熟的恢复过程不是 resume = replay，而是：

Resume=Reload+Repair+Reconcile+Replan+Verify \text{Resume}=\text{Reload}+\text{Repair}+\text{Reconcile}+\text{Replan}+\text{Verify}

  • Reload：读取最新快照与后续事件。
  • Repair：清理不完整的工具对、孤立消息和不兼容旧字段，重建合法输入。
  • Reconcile：向文件系统、Git、进程、数据库或业务 API 查询真实状态。
  • Replan：根据当前世界而不是旧计划，重新选择下一个动作。
  • Verify：确认恢复没有造成重复副作用，并重新校验最终交付标准。

一套可恢复的AI Agent runtime，至少要保存四类状态：

  1. 第一类是语义状态：包括目标、约束、决策、错误、未完成任务和下一步。这部分可由压缩摘要和计划文件承载。
  2. 第二类是对话与事件状态：包括消息 ID、父子关系、工具调用、工具结果、压缩边界、时间戳和分支。这部分应使用追加式日志或数据库事件表，而不是只保存一份可被随意覆盖的“最新对话”。
  3. 第三类是环境状态：包括当前工作目录、Git commit 与 diff、文件快照、运行进程、数据库版本、外部任务 ID 和业务资源状态。它们是检查副作用的真相来源。
  4. 第四类是控制状态：包括当前模式、权限、已批准操作、执行预算、重试次数、子 Agent 关系、人工审批和停止条件。控制状态不应从模型的自然语言摘要中“猜”出来。

从实现上看，恢复通常使用“快照 + 事件重放”：

S_{\text{recovered}}=\operatorname{Reduce}\left(S_{\text{snapshot}},E_{k+1:n}\right)

系统先读取最新快照 S_{\text{snapshot}}，再将快照之后的事件 E_{k+1:n} 按顺序重放，得到恢复状态。但在AI Agent系统里，这还不够：所有停在 DISPATCHED 的外部动作都必须再对真实世界做一次对账。

成熟的AI Agent runtime 的连续性链路，会把压缩与恢复接成一个闭环，可以抽象成以下八个步骤：

  1. 追加事件：用唯一 ID 记录用户输入、模型决策、工具意图、工具结果和审批。
  2. 周期快照：将当前计划、权限、子任务、外部引用与恢复点写入持久层。
  3. 分层压缩：先清理噪声，再压缩旧工具结果，最后才对旧历史做语义摘要。
  4. 保留近端工作集：保留尚未闭合的 API 轮次、工具配对和最近原始消息。
  5. 中断检测：区分正常完成、用户取消、请求未开始、工具执行中断和结果未持久化。
  6. 状态重建：从快照和日志重放语义、事件、环境与控制状态。
  7. 环境对账：查询不确定动作的真实结果，并用幂等、补偿或人工复核解决冲突。
  8. 重规划与验证：根据当前真实世界选择下一步，完成后做端到端验收。

【如何评估上下文压缩与中断恢复：不要只看压缩率】

很多团队进行上下文压缩与中断恢的效果校验时，会把评估结果写成一句话：“上下文从 100K Token 压到了 20K Token，压缩率 80%，效果很好”。

这句话可能完全正确，也可能完全错误。

假设Codex正在修改一个项目：它已经读过 12 个文件，排除了两条错误方案，改了一个核心函数，刚刚写入磁盘，测试还没有跑完。就在工具已经执行、结果还没来得及写回会话时，进程被杀掉了。

重启后，如果AI Agent 重新打开文件、检查 git diff、确认补丁确实存在，然后继续跑测试，这是一次成功恢复。如果它忘记了“为什么不能走方案 B”，又把同一个补丁打了一遍，甚至把已经成功的发布动作再发一次，那么它即使只用了 20K Token，也不能算成功。

Rocky认为，上下文压缩和中断恢复的评价，最终不是评价“大模型的上下文窗口压缩到多少Tokens”，而是评价“长时任务经过压缩和中断之后，是否仍然能持续稳定的进行和正确推进”。

可以把评估对象想象成三本账：

  1. 记忆账：该记住的有没有丢。 用户目标、硬约束、验收标准、关键决策、失败原因、文件路径和未完成任务，是否还能被准确找回。
  2. 动作账：刚才到底做了什么。 哪些工具已经发出，哪些已经成功，哪些失败，哪些处于 UNKNOWN，每个动作能否找到参数、证据和外部任务 ID。
  3. 责任账：接下来还能不能安全地做。 恢复后的权限、审批、预算、工作区和外部世界是否仍然有效，下一步是否会重复写入、重复发布或越过安全边界。

这三本账缺一不可。只看第一本，得到的是“记忆很好的聊天机器人”；只看第二本，得到的是“日志完整但不会继续工作的执行器”；三本账都能对上，才接近真正可交付的AI Agent。更完整的评价指标应包括：

指标要回答的问题
Token 减少率压缩真正节省了多少输入成本？
关键信息召回率目标、约束、决策、错误和待办是否被保留？
协议完整率工具配对、消息边界和引用是否仍然合法？
恢复正确率重启后是否找到正确的未完成任务？
重复副作用率是否重复执行了已成功的发布、写入或修改？
恢复时间从重启到重新开始有效工作需要多久？
重新读取成本恢复后为了找回工作链路，重读了多少文件和外部数据？
压缩循环率压缩后是否立即再次触发压缩，形成资源黑洞？

有人会认为，随着大模型上下文窗口从 128K 走向 1M，未来再走向更长的上下文容量，上下文压缩终将成为一种过渡技术。这个判断只看到了容量，没有看到成本、注意力、缓存、延迟和执行时间。

大模型的上下文窗口变大后，AI Agent不会只用它来完成原来的短任务，而会应用于更大的代码库、更长的调研、更多的工具与更长的时间周期的任务。存储容量的提升，往往会被新任务规模迅速吃掉。

更强的基础大模型会吸收一部分低级压缩工作，例如写出更完整的摘要、识别更多关键信息。但大模型不会自动替代事件日志、幂等键、状态快照、权限管理、环境对账和端到端验收等AI Agent工程级操作。这些能力不是大模型的附件，而是AI Agent runtime的基础设施。

这就是 Rocky 对 AI Agent 上下文压缩与中断恢复的核心判断：

上下文压缩不是为了让AI Agent提炼出任务核心细节后并聚焦任务核心方向；中断恢复是为了让AI Agent在进程消失后仍然对已经发生的动作负责，并持续正确的推进未完成过程。

3. AI Agent的核心大脑——主流LLM/AIGC大模型介绍

3.1 LLM/AIGC大模型在AI Agent系统中的核心作用

Rocky认为，在 AI Agent 系统中，最重要的核心模块依然是 LLM/AIGC 大模型。

如果说上下文工程、工具调用、Memory、RAG、MCP/A2A、Skills、Harness Engineering等是AI Agent的操作系统与配套设施，那么LLM/AIGC大模型就是AI Agent的“大脑”。这个大脑决定了AI Agent能不能理解复杂意图，能不能拆解任务，能不能在不完整信息下做决策，能不能稳定调用工具，能不能在失败后重新规划，能不能把模糊目标转化为可执行步骤，最终实现任务的高效、稳定、正确完成。

但这里有一个非常容易被误解的地方：

LLM大模型提供的不是一个“可靠的内部知识库”，而是一套“解决问题的核心能力引擎”。

所以Rocky一直强调：LLM大模型训练的本质，是对知识、技能和任务模式进行“有损压缩”；而LLM大模型推理的本质，是在当前上下文中重构一条最可能有用的解决路径。

这也解释了为什么大模型能力很强，同时为什么大模型会幻觉。它能力强，是因为它学习压缩了大量通用模式，可以迁移到从写作、代码、数学、视觉理解、数据分析到AI Agent 规划的不同任务里。它存在幻觉，是因为它不是以数据库检索方式返回事实，而是在上下文约束下生成最可能的内容。

从这个角度看，大模型始终会存在幻觉——不管参数规模是从14B到32B，还是扩大到235B、671B，甚至突破1T，幻觉都不会消失。因为大模型训练的本质，是对知识信息进行一种“有损压缩”。

而AI Agent系统要做的事情，就是把LLM大模型能力放进一个可执行、可验证、可治理的系统里。

换句话说，AI Agent不是为了依赖大模型，而是为了给大模型带来更加强劲的综合能力。

如果我们使用的LLM/AIGC大模型足够优秀，就有成为AI Agent领域的“爱因斯坦”的可能性；如果选择落后的LLM/AIGC大模型，则最多成为AI Agent领域中的“比较聪明的普通人”。

总的来说，Rocky认为LLM/AIGC大模型决定AI Agent 的能力上限，AI Agent系统工程决定整体能力能否稳定商业化落地。

未来几年，大模型参数规模会变化，推理架构会变化，多模态能力会变化，模型价格会下降，开源与闭源路线会继续竞争。但真正具备跨周期价值的，是我们要深刻理解这些大模型在AI Agent系统中承担的核心角色。

3.2 LLM/AIGC大模型在AI Agent系统中的六个具体角色

为了更容易理解，我们可以把大模型在AI Agent系统中的作用拆成六个角色。

【第一，Planner：任务规划器】

Planner 负责把用户目标拆成步骤。它要回答：先做什么，后做什么，哪些步骤可以并行，哪些地方需要用户确认，怎样判断任务完成。

这里最重要的是推理能力、目标保持能力和失败恢复能力。Planner 不是写一个漂亮计划，而是生成一条可执行路径。

【第二，Tool Router：工具路由器】

Tool Router 负责选择工具、构造参数、理解工具返回值、处理工具错误。

如果模型工具调用能力不稳，Agent 就会出现各种奇怪问题：该搜索时不搜索，该读文件时凭空编，参数格式错误，API 返回失败后还继续编故事。工具路由能力越强，Agent 越接近真实自动化系统。

【第三，Memory Reader：记忆读取器】

Memory Reader 负责从长期记忆、历史会话、用户偏好、项目文档和知识库中提取相关信息。

这里的关键不是把所有历史塞进上下文，而是让模型判断哪些历史真正相关。Agent 的记忆不是越多越好，而是越准越好。

【第四，Multimodal Perceptor：多模态感知器】

多模态模型负责理解图片、截图、表格、PDF、音频、视频和 UI。

当 Agent 进入真实工作现场后，多模态能力会越来越重要。因为很多任务线索不是写在文本里，而是藏在界面、图表、截图、视频帧和文件版式中。

【第五，Executor：执行器】

Executor 负责把规划转化为具体输出：写代码、写文章、生成图像、编辑表格、调用 API、整理报告。

执行器不一定总是最强模型，有时更需要便宜、稳定、快速、可批量调用的模型。真正成熟的 Agent 系统，会把高价值推理和低价值重复执行分开。

【第六，Evaluator：评估器】

Evaluator 负责检查任务是否完成，结果是否正确，是否存在风险。

这一步非常关键。没有 Evaluator 的 Agent，本质上就是“会行动的生成器”；有了 Evaluator，Agent 才开始接近可靠系统。

【模型选型框架：不要选最强模型，要选最合适的大脑组合】

很多人构建AI Agent系统的第一反应是：哪个大模型最强，就用哪个大模型。

这个思路在 demo 阶段没问题，但在生产阶段一定会遇到成本、延迟、稳定性、权限、合规、可控性的问题。

Rocky 更建议用一个模型选型矩阵：

最强大模型适合做关键判断，但不适合承担所有低价值调用。便宜大模型适合做重复执行，但不能承担高风险决策。国产大模型适合本土业务和私域场景，但也要关注推理、工具调用和生态成熟度。开源大模型适合可控部署，但需要团队具备更强工程能力。多模态大模型能扩展入口，但仍需要工作流和验证机制兜底。

3.3 GPT-5.6系列讲解

GPT系列闭源大模型长期代表了通用大模型能力的最前沿方向。对AI Agent来说，GPT系列最大的价值是把通用推理、代码能力、多模态理解、工具调用和产品生态放在同一个Codex系统里。

在OpenAI最新的公开发布模型中，GPT-5.6-sol 被定位为复杂推理和代码任务的旗舰，代表 GPT 系列最强推理、多模态和Agentic能力；GPT-5.6-terra 侧重能力与成本平衡；GPT-5.6-luna 面向成本敏感型工作负载。三者均公开标注约 1.05M 上下文、128K 最大输出，并支持 Functions、Web search、File search、Computer use 等工具能力。

从AI Agent系统角度看，GPT 系列的核心特点可以概括为四点：

  1. 通用推理能力强，适合作为AI Agent系统的主 planner。Planner 是 Agent 系统里最接近“大脑前额叶”的部分。它要理解目标，拆分步骤，判断工具顺序，决定什么时候终止，什么时候继续。GPT 系列这类前沿模型通常更适合作为高复杂度任务的规划模型，尤其是在代码修复、研究写作、数据分析、复杂问答、多文档整合和跨工具任务中。
  2. 工具调用与结构化输出能力成熟，适合作为 tool router。AI Agent 真正落地时，很多失败并不是模型不知道答案，而是工具参数写错、JSON 格式不稳、调用时机不对、错误后不会恢复。GPT 系列在 function calling、schema following、代码生成和多轮工具协作上的生态成熟度较高，因此更适合放在需要高可靠工具编排的位置。
  3. 多模态能力让AI Agent 从文本系统走向工作现场。AI Agent不可能永远只处理文字。截图、PDF、网页、表格、图像、视频帧、UI 元素，都会成为真实任务的一部分。GPT 系列的多模态能力，让它可以在 Agent 系统中承担“看见现场”的角色：读图、读表、看界面、理解视觉布局，再把这些信息转化为后续工具调用或文本输出。
  4. 生态完整，适合构建生产级AI Agent 工作流。GPT系列背后的 OpenAI 生态以及Codex产品，对开发者构建AI应用有较强支撑。

3.4 Claude Fable 5系列讲解

Anthropic当前把 Claude Fable 5 放在最强大模型的位置，把 Claude Opus 5 作为复杂 Agentic Coding 和企业任务的起点，把 Claude Sonnet 5 作为能力、成本和延迟更平衡的选择。Fable 5、Opus 5、Sonnet 5 均标注 1M token 上下文和 128K 最大输出。

Claude 5 系列更适合长上下文阅读、代码库理解、规范遵循和高风险变更前的审慎规划。对 Claude Code 这类工作流，模型不是一次生成全部代码，而是持续读取环境、提出变更、调用工具、检查差异，再决定是否继续。

在AI Agent系统中，Claude系列模型特别适合承担三类角色：

  1. 长文档与长任务上下文的理解器。很多 Agent 任务不是问一句答一句，而是要读大量材料：产品文档、论文、代码库、合同、研报、历史会话、用户需求、设计稿、日志文件。长上下文能力不只是“能塞更多 token”，而是能在长材料中保持主题、结构和细节的一致性。Claude 系列在长文本阅读和综合表达上有优势，因此很适合做研究型、写作型、代码理解型 Agent 的上下文处理核心。
  2. 复杂写作与高质量表达生成器。对内容型 Agent 来说，大模型不是简单生成段落，而是要形成结构、判断、风格和读者节奏。Claude Opus 这类模型通常更擅长长篇结构化表达、语气控制和复杂观点展开。它适合用于文章润色、研究报告改写、产品文档生成、政策文本解析、客服知识库回答等任务。
  3. 审慎型推理与安全边界控制器。Claude 系列长期强调安全、对齐和审慎表达。在 Agent 系统中，这类能力很重要。因为 Agent 一旦能调用工具，就可能触碰真实权限：发邮件、改文件、访问数据库、执行命令、调用支付或业务 API。一个更审慎、更愿意说明不确定性和风险的模型，适合放在高风险工具调用前后的审核节点。

但Claude也不是所有 Agent 场景的最优解。如果任务高度依赖低延迟、高频工具调用、极强代码自动化、复杂多模态执行或成本敏感的批量任务，就需要结合更便宜、更快、更专门的模型做分层调度。

Rocky认为，Claude系列模型更适合做AI Agent 系统里的“深度理解与高质量判断层”，而不是所有任务都让它亲自执行。

3.5 DeepSeek-v4系列讲解

DeepSeek-v4系列必须单独拿出来讲。因为它对 AI Agent 的意义，不只是“又一个国产大模型”，而是让很多开发者第一次非常直观地意识到：强推理大模型不一定只能以昂贵、封闭、难部署的方式存在。

DeepSeek-v4-Flash和DeepSeek-v4-Pro，两者均为 1M 上下文、最大输出 384K，并支持 thinking/non-thinking、JSON Output、Tool Calls、Responses API、Anthropic API 和 Chat Prefix Completion；FIM 补全仅在 non-thinking 模式可用。DeepSeek-V4系列适合做成本敏感的推理执行器、代码补全器和多模型路由中的大规模工作节点。thinking 模式用于复杂规划与调试，non-thinking 模式用于低延迟分类、抽取和简单工具路由。

从 2025 年 DeepSeek-R1 引发全球关注开始，DeepSeek 这条路线就有一个非常鲜明的技术标签：用更高工程效率、更强强化学习推理能力、更开放的模型权重和更低调用成本，去挑战大家对前沿大模型成本结构的既有认知。

对AI Agent系统来说，DeepSeek系列的价值可以拆成五个层面：

  1. DeepSeek-R1 证明了推理能力可以通过强化学习路线被显著放大。
  2. DeepSeek-V系列的 MoE 架构提供了高性价比推理底座。
  3. DeepSeek的代码和数学能力，非常适合工程型AI Agent。
  4. DeepSeek的开放模型权重和蒸馏路线，让AI Agent 团队可以拥有更多本地控制权。闭源模型的好处是能力强、接口成熟、维护省心；问题是成本、数据边界、定制空间和供应商依赖。开源或开放权重模型的价值，不只是“免费”，而是可控、可部署、可微调、可蒸馏、可与企业私域系统深度结合。
  5. DeepSeek API 的 OpenAI / Anthropic 兼容格式，降低了 Agent 接入成本。

Rocky认为，DeepSeek系列对AI Agent的真正价值，不在于它短期是不是某个榜单第一，而在于它把三件事同时放在了一起：强推理能力、低成本调用、开放可控生态。

这三者组合起来，会让 DeepSeek 成为很多AI Agent 系统里的重要核心大模型，尤其适合代码型Agent、研究型Agent、批量执行型Agent、企业业务Agent、本地部Agent 和成本敏感型Agent。

这才是 DeepSeek 系列在 AI Agent 系统中的跨周期价值。

3.6 GLM-5.2介绍

智谱官方将 GLM-5.2 定位为面向长任务时代的旗舰模型，强调真正可用的 1M 上下文、项目级工程上下文、长程任务执行、工程规范遵循、工具调用与 MCP，最大输出示例为 65536 token。

GLM-5.2适合中文企业环境中的项目级 Planner、工程规范审查器和多端调试执行器。官方推荐场景包括跨文件重构、移动端 ADB/logcat 调试、截图和运行日志结合分析。

GLM-5.2最擅长的工作：

  • 中文需求、工程规范、接口契约和企业内部文档的统一理解。
  • 多文件、多步骤、跨端工程任务。
  • MCP 和 Function Calling 驱动的国内工具链整合。

3.7 Kimi K3介绍

Kimi官方把Kimi K3 定位为旗舰模型，面向长程编程和端到端知识工作，提供 1,048,576 token 上下文；模型始终推理，可通过 reasoning_effort=low/high/max 调节推理强度，默认 max。

Kimi K3 适合研究型 Agent、代码 Agent 和需要长时间保持任务线索的知识工作 Agent。它的关键组合是：长上下文、持续推理、自动上下文缓存、Tool Calls、JSON Schema、tool_choice 和动态工具加载。

4.1 深入浅出通俗易懂完整讲解Function Calling核心基础原理

Rocky认为Function Calling本质上是LLM/AIGC大模型能够调用外部工具和API的能力。我们在使用大模型的Function Calling能力时，首先需要定义相关的Functions，通过系统提示词告知大模型。当用户输入问题时，大模型首先需要判断是否使用Function，如果需要使用Function，再确定具体使用哪个Function。如果不需要使用Function，则直接生成回答。

如果需要调用Function，大模型会返回一个JSON或者XML格式信息，其中包括了需要调用的Function名称、参数名及对应的参数值等传参信息。

这时候整个Function Calling的流程可以分为：

  1. LLM/AIGC大模型思考： 用户输入问题，AI Agent中的核心LLM/AIGC大模型先对问题进行分析思考。
  2. Function Calling行动： 如果问到了股票涨跌问题，则需要LLM/AIGC大模型分析出需要调用的Function以及要传入的参数。
  3. Function Calling响应：Function运行后返回输出结果，LLM/AIGC大模型再将答案整理成自然语言回复给用户。
  4. 流程的循环迭代：除了一次性将输出结果发送给用户，我们还可以设置循环迭代的Function Calling过程，让LLM/AIGC大模型带着回答和问题进行多次思考，多次调用Function，使得输出结果完善。但是多次迭代时，也可能会引入大模型的“幻觉”，从而使得回复内容有所偏差。

可以看到，Function Calling让LLM/AIGC大模型获得了调用外部Function的能力，这个Function可以是一个代码函数，也可以是一个API、数据库、搜索引擎等。

4.3 LLM/AIGC大模型如何学习到Function Calling能力

通过上面几个小节的学习，我们已经知道了Function Calling的原理和用法。我们接下来更进一步思考，Function Calling能力不是LLM/AIGC大模型在预训练阶段原生具备的，我们该如何让LLM/AIGC大模型学习到Function Calling能力呢？

当前AI业界主流的方法是通过监督微调（Supervised Fine-tuning, SFT）训练来实现LLM/AIGC大模型对Function Calling能力的学习，而不是在预训练阶段从零开始专门训练。当前AI业界具备Function Calling能力的大模型包括DeepSeek系列、GPT-4o系列、Claude系列、Qwen系列、Gemini系列等。

同时在微调训练前，LLM/AIGC基础大模型需要先具备良好的指令遵循和代码/结构化数据生成能力。

Function Calling能力微调训练的核心思想：

  1. 获取识别意图（Intent Recognition）能力：理解用户的请求是否需要借助外部工具/函数来完成，而不是直接生成文本回答。
  2. 获取参数提取与格式化（Argument Extraction & Formatting）能力：如果需要调用函数，正确地从用户请求中抽取出所需的参数，并按照预先定义的格式（JSON、XML等）生成函数调用的指令。

1. 训练数据集制作：可以说数据集整理是整个微调过程最重要的一步，因为我们需要构建一个包含Function Calling场景的指令微调数据集，让基础大模型能够充分的学习参数与格式化内容。每个数据样本通常包含以下内容：

  1. 功能名称：该功能的唯一识别标识
  2. 功能说明：用通俗语言明确描述功能用途和应用情境，帮助大模型判断调用时机
  3. 参数定义：规定功能接受的输入参数。类型：通常为”对象”；属性明细：详细说明每个参数的名称、数据类型和具体含义；必需参数：明确必须提供的参数项目。

Rocky再举一个通俗易懂的例子，帮助大家更好的理解AI Agent中的Function Calling的触发流程：

第一步：用户发起请求 用户输入：”请查询广州明天的天气情况，并将结果通过邮件发送给李四”

第二步：大模型初次响应（功能调用） 模型识别需要调用天气查询功能，生成结构化数据：
{
  "调用的功能": "get_weather",
  "参数内容": {
    "城市名称": "广州",
    "查询日期": "明天"
  }
}

第三步：外部程序执行 应用程序捕获该数据结构，调用实际的气象数据接口

第四步：结果反馈至模型 将API返回的气象信息格式化后提供给模型：
get_weather功能执行结果：
{
  "气温": "28°C",
  "天气状况": "多云转晴"
}

第五步：模型再次响应（可能继续调用功能或生成最终回复） 模型基于气象结果，准备执行邮件发送任务，生成：
{
  "调用的功能": "send_email", 
  "参数内容": {
    "收件人地址": "李四",
    "邮件主题": "明日广州天气信息",
    "邮件正文": "明日广州预计气温28°C，天气状况为多云转晴。"
  }
}

第六步：外部程序执行 应用程序调用邮件发送服务

第七步：执行结果反馈 向模型确认邮件发送状态

第八步：模型生成最终回复 模型向用户输出总结性回应：”已成功查询到广州明日天气为28°C，多云转晴，相关信息已通过邮件发送给李四。”

更多样例数据集大家可以参考：https://huggingface.co/datasets?search=function-calling，里面包含了很多经典的Function-Call数据集。

2. 选择基础模型：选择一个具备强大指令遵循能力的预训练LLM/AIGC大模型(例如DeepSeek系列、GPT-4o系列、Claude系列、Qwen系列、Gemini系列等)。

3. 格式化训练数据：将每条数据样本组合成大模型可以理解的格式。通常是将数据集中的“用户输入”和“可用函数/工具描述”拼接起来作为模型的输入(Prompt)，将“期望的输出”（无论是JSON、XML函数调用还是文本回答）作为目标输出(Completion/Target/Label)。需要使用特定的分隔符或模板来区分不同部分。

4. 进行微调训练：使用标准的SFT方法（全参数微调或训练LoRA）在特定数据集上进行微调训练。大模型的优化目标是最小化预测输出和期望输出之间的差异（例如使用交叉熵损失）。大模型通过学习这些样本，学会根据用户输入和可用函数描述，决定是直接回答还是生成特定格式的函数调用JSON、XML。

经过上述的微调训练流程，我们就能获得具备Function Calling能力的LLM/AIGC大模型了。

5. AI Agent的Hooks核心基础知识

Rocky 认为，理解 AI Agent，我们不能只盯着大模型、工具调用、RAG、Memory、MCP、Workflow 这些显性的模块。

这些模块当然重要。但如果我们真的把AI Agent系统放进生产环境，就会很快遇到一个更底层的问题：大模型负责生成意图，工具负责执行动作，但谁来决定动作在什么时候可以发生、发生前要不要检查、发生后要不要记录、失败后要不要恢复？

而这个问题，就是 Hooks 要解决的问题。

很多读者第一次看到Hooks，会把它理解成“回调函数”或者“插件机制”。这个理解没有错，但还是太浅显了。

在真正的AI Agent系统里，Hooks不是简单的callback，而是AI Agent运行时的“执行切面”。它可以插入在用户输入前、工具调用前、工具调用后、权限申请时、会话启动时、上下文压缩前后、子 Agent 结束时、文件变化时、配置变化时、任务创建或任务完成时。它让 Agent 从一个模型驱动的黑盒，变成一个可以被治理、被审计、被扩展、被恢复的执行系统。

换句话说：AI Agent 的能力上限由模型和工具决定，但AI Agent的工程可靠性，往往由Hooks决定。

这句话听起来有点“工程味”，但背后的逻辑非常简洁本质。

大模型是概率系统。它的每一次输出，本质上都是在当前上下文中生成一条最可能的路径。工具调用则是现实系统。它可能改文件、跑命令、发请求、调数据库、发邮件、创建工单、操作浏览器、控制机器人。二者一旦连接，AI Agent 就不再只是“回答问题”，而是在真实世界里“造成后果”。

所以，成熟的AI Agent系统一定需要一个机制，把“大模型想做什么”和“系统允许它做什么”分开。

Hooks 就是这层机制的核心形态之一。

5.1 Hooks 的本质：Agent 生命周期中的可编程控制点

如果用一句话定义 Hooks：

Hooks 是 Agent 运行时在关键生命周期节点暴露出来的可编程控制点，用来实现拦截、增强、验证、审计、通知和恢复。

这里有几个关键词非常重要。

第一，Hooks 是“生命周期节点”，不是随便插一段代码。

一个 Agent 从收到用户输入，到构造上下文，到模型推理，到选择工具，到申请权限，到执行工具，到读取结果，到继续推理，到停止响应，中间有很多天然的边界。Hooks 正是插在这些边界上。

第二，Hooks 是“可编程控制点”，不是固定策略。

同一个 PreToolUse，可以用来做权限校验，也可以用来做命令白名单，也可以用来做风险扫描，也可以用来把即将执行的动作发给企业审计系统。Hooks 的价值不是某个固定功能，而是把系统边界开放给开发者、团队和组织。

第三，Hooks 的目标不是让 Agent 更炫，而是让 Agent 更可控。

一个没有 Hooks 的 Agent，像一个很聪明但没有刹车、没有仪表盘、没有安全员的自动驾驶系统。它可以很快，也可能很危险。一个设计良好的 Hooks 系统，则像给 Agent 加上刹车、后视镜、黑匣子、红绿灯和交警。

Rocky 在看 Codex、Claude Code、Agno 这些 Agent 系统时，一个很强烈的体感是：

越接近真实生产的 Agent，越不会把“让模型自由发挥”当作核心卖点，而是会把权限、审计、上下文、工具、记忆、异常处理拆成可治理的运行时能力。

Hooks 正是这个运行时治理层的代表。

5.2 为什么 Agent 必须有 Hooks：从“能调用工具”到“能安全执行”

早期很多 Agent Demo 的逻辑非常简单：

用户给一个目标，模型思考，模型选择工具，工具返回结果，模型继续思考，直到输出最终答案。

这个流程看起来很自然，但放到真实环境里会马上暴露问题。

比如，一个 Coding Agent 准备执行：

rm -rf dist

这条命令有可能是合理的构建清理，也可能是误删路径的前奏。

再比如，一个数据 Agent 准备查询数据库：

SELECT * FROM users;

它可能只是想看表结构，也可能无意中触碰了敏感数据。

再比如，一个企业 Agent 准备调用邮件工具：

Send email to all customers

这已经不是“生成内容”的问题，而是“真实业务后果”的问题。

因此，Agent 系统里至少需要回答六个问题：

  1. 这个动作是否允许执行？
  2. 这个动作是否需要用户确认？
  3. 这个动作是否命中了组织策略？
  4. 这个动作执行前后是否需要记录？
  5. 这个动作失败后是否要重试、降级或回滚？
  6. 这个动作产生的结果是否要进入 Memory、Trace、审计日志或下一轮上下文？

这些问题如果全部写死在主循环里，Agent 很快会变成一坨复杂的业务 if-else。

Hooks 的价值，就是把这些横切逻辑从主流程里抽出来。

模型主循环仍然负责“理解、规划、生成、调用”，Hooks 负责在关键节点上做“检查、补充、拦截、记录、触发”。这就是软件工程里典型的切面思想，只不过在 AI Agent 里，它的意义被放大了。

因为 Agent 不只是处理数据，而是在执行不确定模型生成的动作。

5.3 一个完整 Hooks 系统的五个核心组成

Rocky 认为，判断一个 Agent 框架的 Hooks 是否成熟，不要只看它有没有 before 和 after 回调，而要看它是否具备下面五个组件。

【触发点：Hook Event】

触发点决定 Hook 在什么时候执行。

在成熟的 Coding Agent 或通用 Agent 系统里，常见 Hook Event 包括：

Hook Event触发时机典型价值
UserPromptSubmit用户提交 Prompt 后、模型处理前Prompt 过滤、敏感意图识别、补充上下文、任务路由
SessionStart会话启动、恢复、清空、压缩后重启注入环境信息、项目规范、团队策略、默认上下文
InstructionsLoaded指令文件或规则被加载时审计规则来源、防止错误规则污染上下文
PreToolUse工具执行前权限校验、命令拦截、参数改写、风险扫描
PermissionRequest系统准备弹出权限确认时自动审批、自动拒绝、接入企业审批流
PostToolUse工具执行成功后结果审计、自动格式化、写入 Memory、触发后续任务
PostToolUseFailure工具执行失败后错误分类、重试建议、失败恢复、告警通知
Notification系统发送通知时企业 IM 通知、桌面通知、异步任务提醒
Stop主 Agent 即将结束回答前结果验收、是否需要继续执行、质量门禁
SubagentStart子 Agent 启动时子任务注册、预算分配、隔离上下文
SubagentStop子 Agent 即将结束时子任务验收、结果合并、失败返工
PreCompact上下文压缩前补充压缩指令、防止重要信息丢失
PostCompact上下文压缩后审计摘要质量、恢复关键状态
ConfigChange配置文件变化时阻止不可信配置生效、记录团队策略变更
CwdChanged / FileChanged工作目录或文件变化时自动加载环境变量、触发索引更新、刷新上下文
SessionEnd会话结束时清理资源、保存状态、写入最终审计

这张表真正要表达的不是某一个框架支持了多少事件，而是一个更本质的判断：

Agent 的生命周期越长、执行半径越大、协作角色越多，它就越需要细粒度的 Hook Event。

简单问答产品可能只需要输入输出过滤。Coding Agent 需要工具前后 Hook。企业流程 Agent 需要权限 Hook、审计 Hook、通知 Hook。多 Agent 系统还需要子 Agent 生命周期 Hook。长上下文 Agent 还需要 Compact 前后 Hook。

这就是为什么 Hooks 不是锦上添花，而是 Agent 产品形态复杂化之后的必然基础设施。

【匹配器：Matcher】

触发点解决“什么时候”，Matcher 解决“对谁生效”。

比如同样是 PreToolUse，我们可能只想拦截 Bash，不想拦截 Read；只想拦截 git push，不想拦截 git status；只想拦截 Write 和 Edit，不想拦截搜索工具。

一个通用 Hook 配置大概长这样：

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "python scripts/agent_policy_check.py",
            "timeout": 30
          }
        ]
      }
    ]
  }
}

这个配置的含义很简单：

当 Agent 准备使用 Bash、Write、Edit 这些工具时，先运行一个策略检查脚本。如果检查通过，工具继续执行；如果检查失败，可以阻止工具执行、把原因反馈给模型，或者只把错误展示给用户。

Matcher 是 Hooks 变得可维护的关键。

没有 Matcher，Hook 要么太粗，导致所有工具调用都变慢；要么太细，导致规则散落在代码各处。好的 Matcher 应该同时支持工具名、命令模式、通知类型、会话来源、Agent 类型、文件路径、MCP server 名称等字段。

Rocky 的判断是：

Hooks 系统真正难的不是“能不能执行一个脚本”，而是能不能把 Hook 的作用范围表达清楚。

一个企业级 Agent 如果没有清晰的 Matcher，最后一定会出现两类问题：该拦的没拦住，不该拦的被拦死。

【执行器：Executor】

Hook 被触发后，到底执行什么？

成熟系统通常不会只支持一种执行器，而是支持多种形态。

Hook 类型执行方式适合场景
command执行 Shell 命令或本地脚本本地策略检查、格式化、测试、日志、环境更新
http向外部服务 POST Hook 输入企业审批流、审计平台、风控服务、CI 系统
prompt用一个轻量模型判断 Hook 输入Prompt 分类、结果质量判断、轻量语义检查
agent启动一个小 Agent 做验证复杂验收、代码审查、任务完成度判断
function/callback内部函数回调SDK 内部扩展、插件系统、性能敏感逻辑

这里最值得注意的是 prompt 和 agent 类型。

传统软件的 Hook 通常执行确定性代码。但 Agent 系统里的 Hook，越来越多会调用另一个模型，甚至调用一个子 Agent。

比如 Stop Hook 可以做一件非常有价值的事：

在主 Agent 准备结束任务前，启动一个轻量 verifier，让它检查“计划中的步骤是否真的完成”“测试是否真的运行”“输出是否满足用户目标”。如果 verifier 判断没有完成，就把错误反馈给主 Agent，让主 Agent 继续工作。

这就是 Agent 系统里非常重要的“自我验收”。

但这里也有一个坑：

模型 Hook 不能无限递归。

如果一个 UserPromptSubmit Hook 自己又触发新的用户输入 Hook，或者一个 Stop Hook 启动的 verifier 又触发同类 Stop Hook，系统就会进入递归。成熟实现必须明确避免 Hook 触发 Hook 的死循环，或者对 Hook Agent 做工具限制、轮数限制、超时限制和结构化输出约束。

这也是为什么真实 Agent 工程远比 Demo 复杂。

【返回语义：Hook Result】

Hook 的返回结果不能只用“成功/失败”概括。

在 Agent 系统里，一个 Hook 至少需要表达下面几类语义：

返回语义含义典型场景
allow / success允许主流程继续策略检查通过
block阻止当前动作危险命令、敏感数据、违规工具调用
ask要求用户确认高风险写操作、外部发送、权限扩大
deny明确拒绝命中企业策略、访问越权
retry允许模型重试权限拒绝但可换一种方式完成
append_context给模型补充上下文注入项目规范、测试失败原因、格式要求
mutate_output修改工具返回内容过滤敏感内容、规范 MCP 输出
audit_only不阻塞，只记录合规留痕、行为分析
async_notify后台执行，完成后通知长时间扫描、CI 任务、远程审核

如果 Hook 返回语义设计得太粗，会导致系统很难表达真实业务需求。

比如“测试失败”不一定意味着要终止任务，它更可能意味着要把失败原因反馈给模型继续修复。再比如“权限申请被拒绝”不一定意味着任务失败，它可能意味着模型应该改用只读方式、换一个工具，或者请求用户提供更小权限。

所以，一个好的 Hooks 系统，本质上是在给 Agent 建立一套“运行时语言”：

模型能理解什么是阻塞，什么是警告，什么是审计，什么是可重试，什么是需要用户参与。

【可观测性：Trace、Log、Audit】

Hooks 如果不能被观察，就会变成新的黑盒。

一个成熟系统至少要记录：

  1. 哪个 Hook 被触发；
  2. 触发时的事件类型是什么；
  3. 匹配到了哪个工具、命令、文件或 Agent；
  4. Hook 来源是用户配置、项目配置、本地配置、插件、会话临时配置还是内置规则；
  5. Hook 执行耗时是多少；
  6. Hook 输出了什么；
  7. Hook 是允许、阻塞、失败、取消还是后台执行；
  8. Hook 是否改变了主流程；
  9. 最终 Agent 是否因此改变了计划。

这就是为什么 Agno 这类 Agent 平台会把 tracing、run history、audit logs、human approval 放在非常核心的位置。

Agent 的可观测性不是为了“看起来专业”，而是为了回答一个最现实的问题：

当 Agent 做错事时，我们能不能知道它为什么做错；当 Agent 做对事时，我们能不能复用它做对的路径。

没有 Hooks 和 Trace，Agent 的错误很难复盘。没有复盘，就没有可靠性提升。

5.4 以 Codex 为例：Hooks 如何把“会写代码”变成“可协作工程系统”

可以用 Codex 这样的 Coding Agent 来理解 Hooks。

从用户视角看，Codex 似乎只是在读代码、改代码、跑命令、写总结。但从系统视角看，一个 Coding Agent 的运行链路里天然存在大量 Hook 位点。

比如：

  1. 用户提出任务后，需要先读上下文，而不是立刻修改代码；
  2. 执行命令前，需要判断命令是否安全、是否需要用户授权、是否会写出工作区；
  3. 编辑文件前，需要理解已有改动，不能回滚用户修改；
  4. 应用补丁时，需要使用结构化 patch，而不是随意覆盖文件；
  5. 跑测试失败后，需要读取错误、定位原因、继续修复；
  6. 长时间工作时，需要向用户汇报当前进展；
  7. 最终回答时，需要说明改了什么、验证了什么、哪些事情没做成。

这些行为如果写成一条主流程，会非常僵硬。但如果抽象成 Hooks，就是一套更清晰的执行控制面：

Codex 行为对应 Hook 思想
读仓库结构后再动手SessionStart / InstructionsLoaded / context hook
命令执行前判断沙箱与权限PreToolUse / PermissionRequest
编辑前说明要改什么human-in-the-loop hook
使用 apply_patch 而不是粗暴覆盖tool policy hook
测试失败后继续定位PostToolUseFailure
每隔一段时间同步进展Notification / progress hook
最终汇总验证结果Stop / finalization hook

Rocky 认为，Coding Agent 是理解 Hooks 的最佳场景之一。

因为代码世界里，Agent 的每个动作都能留下痕迹：文件 diff、命令输出、测试结果、错误日志、权限提示、git 状态。这些痕迹天然适合被 Hooks 捕获、检查和治理。

真正强的 Coding Agent，不只是“模型会写代码”，而是它有一套工程化运行时，知道什么时候该读、什么时候该问、什么时候该拦、什么时候该测、什么时候该停。

这也是 Agent 从玩具到工具的关键分界线。

5.5 从 Claude Code 类系统看 Hooks：生命周期、配置来源与权限边界

Claude Code 这类 Coding Agent 的 Hooks 设计，体现了一个更偏产品级的思路：Hooks 不只是开发者内部扩展，而是用户、项目、插件、会话、平台都可以参与的运行时机制。

这里有几个设计非常值得长期学习。

【Hooks 有作用域，不是全局一锅粥】

Hooks 的配置来源可以分成多层：

来源含义
User Settings用户个人级配置
Project Settings项目级配置
Local Settings本地机器级配置
Plugin Hooks插件提供的 Hook
Session Hooks当前会话临时 Hook
Built-in Hooks系统内置 Hook
Policy Settings企业或组织级策略

这个分层非常重要。

个人用户可能希望每次 PostToolUse 后自动格式化。项目团队可能希望每次写文件后运行 lint。企业组织可能希望所有高风险命令都进入审计。当前会话可能临时加一个 verifier，检查任务是否完成。

如果这些规则都混在一个配置里，系统很快会失控。

所以生产级 Hooks 必须有清晰的作用域和优先级。

Rocky 认为，这里真正的跨周期价值是：

Agent 系统以后一定会越来越组织化，个人 Hook、项目 Hook、企业 Hook、插件 Hook 必须共存。谁能把作用域、优先级、可见性和安全边界设计清楚，谁才有机会成为 Agent 运行时平台。

【Hooks 支持不同执行形态】

Claude Code 类系统里的 Hooks 不只是 shell command，还可以是 prompt、agent、http、function/callback。

这说明 Hooks 已经从传统软件里的“脚本扩展”升级为 Agent Native 的“运行时扩展”。

比如：

  1. command Hook 适合执行本地确定性检查；
  2. http Hook 适合接入外部审批和审计系统；
  3. prompt Hook 适合轻量语义判断；
  4. agent Hook 适合复杂验收；
  5. function/callback Hook 适合 SDK 内部高性能扩展。

这背后有一个很重要的趋势：

未来 Agent 的 Hooks 不会只是代码回调，而会变成“模型 + 工具 + 策略 + 组织流程”的混合控制层。

比如一个企业可以配置：

{
  "hooks": {
    "PermissionRequest": [
      {
        "matcher": "Bash|Write|MCPTool",
        "hooks": [
          {
            "type": "http",
            "url": "https://internal.example.com/agent-approval",
            "timeout": 10,
            "allowedEnvVars": ["AGENT_APPROVAL_TOKEN"]
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "agent",
            "prompt": "Verify that the task is complete, tests were run if needed, and no unrelated files were changed. Use $ARGUMENTS as the run summary.",
            "timeout": 60
          }
        ]
      }
    ]
  }
}

这段配置表达的不是某个具体框架语法，而是一种通用思想：

权限申请交给企业审批服务，任务结束交给一个 verifier Agent 做验收。

这就是 Agent 系统从单体应用走向平台化的典型方向。

【Hooks 必须尊重信任边界】

Hooks 很强，但也很危险。

因为 command Hook 本质上可以执行本地命令。HTTP Hook 可能把上下文发到外部服务。Prompt/Agent Hook 可能读取上下文并生成新的判断。Plugin Hook 可能由第三方提供。

所以成熟系统必须回答：

  1. 当前工作区是否可信？
  2. 哪些 Hook 可以在未信任项目中执行？
  3. 企业托管 Hook 和用户自定义 Hook 谁优先？
  4. 是否允许完全禁用用户 Hook？
  5. 环境变量能不能被 Hook 读取？
  6. HTTP Hook 能不能自动带上敏感 token？
  7. Hook 输出能否进入模型上下文？
  8. Hook 是否可能绕过权限系统？

这也是为什么 Hooks 不是“越开放越好”。

Rocky 认为，Hooks 的安全设计至少要遵循四条原则：

  1. 默认最小权限；
  2. 未信任工作区不执行危险 Hook；
  3. 敏感环境变量必须显式 allowlist；
  4. 企业策略不能被普通 Hook 阻塞或覆盖。

Agent 的本质是自动化执行。Hooks 的本质是给自动化执行加控制面。控制面如果被攻击者控制，风险会比普通工具调用更大。

5.6 Hooks 的通用工程架构

一个通用 Hooks 系统可以抽象成下面这条链路：

Agent Lifecycle Event
        |
        v
Build Hook Input
        |
        v
Find Matched Hooks
        |
        v
Check Scope / Trust / Policy
        |
        v
Execute Hook
        |
        v
Parse Hook Result
        |
        v
Apply Decision
        |
        v
Trace / Audit / Notify

如果写成伪代码，大概是这样：

def run_agent_turn(user_input, state):
    user_input = execute_hooks("UserPromptSubmit", {
        "prompt": user_input,
        "session_id": state.session_id,
    }).maybe_rewrite(user_input)

    messages = build_context(user_input, state)

    while True:
        model_output = llm.generate(messages)

        if model_output.tool_call:
            tool_call = model_output.tool_call

            decision = execute_hooks("PreToolUse", {
                "tool_name": tool_call.name,
                "tool_input": tool_call.input,
                "session_id": state.session_id,
            })

            if decision.blocked:
                messages.append(decision.feedback_to_model)
                continue

            if decision.requires_permission:
                permission = execute_hooks("PermissionRequest", {
                    "tool_name": tool_call.name,
                    "tool_input": tool_call.input,
                })
                if permission.denied:
                    messages.append(permission.reason)
                    continue

            try:
                result = execute_tool(tool_call)
                post = execute_hooks("PostToolUse", {
                    "tool_name": tool_call.name,
                    "tool_input": tool_call.input,
                    "tool_output": result,
                })
                messages.append(post.maybe_transform(result))
            except Exception as error:
                recovery = execute_hooks("PostToolUseFailure", {
                    "tool_name": tool_call.name,
                    "tool_input": tool_call.input,
                    "error": str(error),
                })
                messages.append(recovery.feedback_to_model)
                continue

        if model_output.final_answer:
            stop_decision = execute_hooks("Stop", {
                "answer": model_output.final_answer,
                "session_id": state.session_id,
            })
            if stop_decision.should_continue:
                messages.append(stop_decision.feedback_to_model)
                continue
            return model_output.final_answer

这段伪代码说明了一个关键点：

Hooks 不应该替代 Agent 主循环，而应该包裹 Agent 主循环的关键边界。

Hook 过多，主流程会变慢。Hook 过少，主流程会失控。好的设计，是把 Hook 放在真正有风险、真正有状态变化、真正需要治理的节点上。

6. AI Agent中Skills的核心基础知识

6.1 什么是AI Agent的Skills技术？

Skills（技能）是AI Agent最核心的”动手能力”——它是将大语言模型（LLM）的文本推理能力，转化为可执行、可复用、可组合的具体行动单元的技术。

Rocky打个通俗的比方：

  • 大模型是AI Agent的”大脑”，负责思考、理解和决策
  • Skills是AI Agent的”双手+工具箱”，负责把大脑的想法变成实际结果
  • 没有Skills的AI只能”纸上谈兵”（给建议），有了Skills的AI才能”真刀真枪干活”（直接完成任务）

目前主流的AI Agent系统中，所有”能帮我们做事”的功能（写代码、跑命令、构建项目、生成PPT等），本质上都是它内置或扩展的Skills在发挥作用。

6.2 Skills技术的5大核心原理

【1. 技能的抽象与表示：把”事”打包成”能力模块”】

Skills技术的第一步，是将人类能做的具体工作，抽象成大模型能理解和调用的标准化能力单元。

比如我们以Claude Code为例，其核心技能抽象：


技能类别具体能力底层实现
本地操作读取/编辑/创建文件、运行终端命令、Git提交直接调用操作系统API和本地工具
编码能力代码生成、调试、重构、Lint修复大模型代码理解+文件操作技能组合
项目导航分析项目结构、查找代码引用、解释模块功能全项目上下文索引+语义搜索
外部连接读取Google Drive、更新Jira、发Slack消息MCP（模型上下文协议）统一接口


每个Skill的标准结构都包含3个核心部分：

  • 意图描述：用自然语言说明这个技能能做什么（LLM/AIGC大模型靠它识别什么时候该用这个技能）
  • 输入输出规范：明确需要什么参数、返回什么结果（比如”运行命令”技能需要输入命令字符串，返回输出和退出码）
  • 执行逻辑：实际完成任务的代码或接口（比如调用os.system执行命令，调用Git API提交代码）

【2. 意图理解→任务分解：把自然语言变成技能执行计划】

这是大模型在Skills技术中最核心的作用：将用户的模糊自然语言请求，拆解为有序的、可执行的技能调用序列。

Claude Code的任务分解流程：

  1. 用户输入：”帮我给这个用户登录接口添加手机号验证码功能”
  2. 大模型理解意图：需要在现有登录接口基础上，新增验证码生成、验证、错误处理逻辑
  3. 分解为技能调用序列：
  • 技能1：读取现有登录接口的代码文件
  • 技能2：分析现有代码结构，找到需要修改的位置
  • 技能3：生成验证码生成和验证的代码
  • 技能4：修改登录接口，集成验证码逻辑
  • 技能5：运行单元测试，验证功能是否正常
  • 技能6：如果测试失败，分析错误并修复代码
  • 技能7：提交代码变更，生成提交信息

关键特点：任务分解不是一次性的，而是动态迭代的——大模型会根据前一个技能的执行结果，调整后续的技能调用计划。

【3. 闭环执行与反馈：不是一次性调用，是持续迭代】

这是Skills技术和传统”工具调用”最本质的区别：传统工具调用是”大模型发指令→工具执行→返回结果”的单次交互，而Skills是“执行→反馈→调整→再执行”的闭环过程。

Claude Code的闭环执行示例（调试bug）：

  1. 用户粘贴错误信息：”登录接口返回500错误，日志显示NullReferenceException”
  2. 技能调用：读取登录接口代码→运行测试复现错误
  3. 执行结果：测试失败，错误指向第45行user.email为空
  4. 大模型分析：用户可能未传入email参数，需要添加空值检查
  5. 技能调用：修改代码添加空值检查→重新运行测试
  6. 执行结果：测试通过
  7. 技能调用：提交修复代码

【4. 技能组合：像搭积木一样完成复杂任务】

Claude Code严格遵循Unix哲学：”做一件事，并且做好它”。每个Skill都是单一职责的小模块，可以像管道一样组合起来，完成极其复杂的任务。

文档中的两个经典组合示例：

  1. 实时日志监控告警： tail -f app.log | claude -p "如果看到任何异常，发Slack消息通知我" 技能组合：实时日志输出 → 日志异常分析 → Slack消息发送
  2. CI自动化翻译： claude -p "如果有新的文本字符串，翻译成法语并提交PR给@lang-fr-team审核" 技能组合：代码变更检测 → 文本提取 → 机器翻译 → PR创建 → 团队通知

可脚本化特性：你可以把Claude Code的技能调用写成Shell脚本或Python脚本，集成到你的CI/CD流水线中，实现完全自动化的开发流程。

【5. 技能扩展：通过MCP连接无限可能】

当内置技能不够用时，Claude Code通过MCP（模型上下文协议） 提供了统一的技能扩展机制，让我们可以连接任何外部工具和服务，甚至编写自己的自定义技能。

7. 零基础深入浅出讲解MCP（Model Context Protocol）、A2A（Agent2Agent）的核心基础知识

7.1 通俗易懂完整讲解MCP的核心基础知识

2024年11月，MCP（Model Context Protocol）开放标准协议横空出世，以破竹之势重新定义AI Agent与外部工具之间的交互方式，让AI智能体安全地连接外部工具和数据源。

MCP协议由Anthropic公司推出，Anthropic创始团队与OpenAI颇有渊源。负责OpenAI研发相关的研究副总裁达里奥·阿莫迪和安全政策副总裁丹妮拉·阿莫迪离职创立了一家与OpenAI有着不同价值观的人工智能公司——正是Anthropic。

到这里，可能会有读者疑惑，到底什么是 MCP协议呢？Don't Worry，Rocky接下来会为大家娓娓道来。

MCP协议旨在为AI大模型提供一种统一的方式来连接外部工具、数据源和服务。我们可以把MCP协议理解为"AI大模型的USB接口" — 制定一个标准化的连接方式，让任何AI Agent里的AI大模型都能即插即用地使用各种工具。

在MCP协议出现之前，每个AI平台都有自己的工具集成方式 — Function Calling、Plugin、Tool Use 等，互不兼容。MCP彻底改变了这一局面：AI工具开发者只需要开发一个 MCP Server，就可以被所有支持 MCP 协议的AI平台使用，包括Codex、Claude Desktop、Cursor以及OpenClaw等。

Rocky认为，MCP协议的核心优势包括：

  • 标准化：一次开发，多平台复用。不再为每个AI平台/AI Agent单独开发兼容。
  • 安全隔离：MCP Server 运行在独立进程中，与AI Agent主进程完全隔离，即使工具崩溃也不影响AI Agent系统的正常运行。
  • 双向通信：不仅可以调用工具（Tools），还可以提供资源（Resources）和提示模板（Prompts）给AI Agent系统。
  • 生态爆发：Anthropic、GitHub、OpenAI等公司纷纷发布官方 MCP Server，社区贡献更是无比繁荣。
  • 开源开放：协议规范完全开源，任何人都可以实现和扩展。

举个例子，AI Agent系统可以通过MCP标准化协议接口实现天气查询、数据库调用、上下文持久化存储、智能设备联动等跨平台协同。可以说MCP协议就是AI Agent领域的“万能社交达人”。

大模型公司可以通过它提升AI Agent服务的兼容性、扩展性与智能化水平，开发者可依托其开放生态快速构建插件化应用，企业亦能借此降低AI集成成本，加速业务创新。作为AI交互领域的关键基础设施，MCP正推动技术生态从“碎片化”走向“一体化”，为智能应用的规模化落地提供核心支撑。

我们再来看一下，MCP协议的具体图解：

我们以OpenClaw为例，在OpenClaw中添加 MCP Server 后，启动时会发生以下流程：

  1. OpenClaw 启动 MCP Server 进程：根据配置文件中的命令（如 npx @anthropic/mcp-server-filesystem），OpenClaw 自动启动 MCP Server 作为子进程。
  2. 协议握手：OpenClaw 通过 stdio 或 SSE 与 MCP Server 建立连接，交换能力列表（支持哪些工具、资源、提示模板）。
  3. 工具注册：MCP Server 提供的所有工具会被注册到 OpenClaw 的工具列表中，AI Agent可以像使用普通Skills一样调用它们。
  4. 运行时调用：当AI决定使用某个MCP工具时，OpenClaw 将请求转发给对应的 MCP Server，等待结果返回后呈现给用户。

MCP Server 在 OpenClaw 中的配置位于 openclaw.json 的 tools 部分。以下是一个典型配置示例：

{
  "tools": {
    "mcp": [
      {
        "type": "stdio",
        "command": "npx",
        "args": ["-y", "@anthropic/mcp-server-filesystem", "/data"],
        "env": {}
      },
      {
        "type": "stdio",
        "command": "npx",
        "args": ["-y", "@anthropic/mcp-server-brave-search"],
        "env": {
          "BRAVE_API_KEY": "your-api-key"
        }
      }
    ]
  }
}

每个 MCP Server 条目包含：type（连接方式，通常为 stdio）、command（启动命令）、args（命令参数）和 env（环境变量，用于传递API密钥等）。

到这里，可能有很多读者会问，MCP与Function Call有哪些区别与关系？

Function Call本质上是大模型的一种原生能力机制，其关注点在LLM大模型如何识别用户意图并生成工具调用指令，作用层级是在大模型推理层面。

而MCP本质上是一个AI Agent系统的通信协议，其关注点在标准化工具与数据源的发现、连接和交互方式，作用层级是在AI Agent系统架构层面。

下面是Rocky总结的MCP和Function Call的功能对比归纳：

维度Function CallMCP
核心功能意图识别与指令生成工具发现与执行标准化
工作阶段模型推理过程中调用指令生成后的执行阶段
技术焦点自然语言到结构化指令的转换跨系统通信、安全控制、资源管理
标准化程度各厂商自有实现（如OpenAI FC）统一的开放协议标准

Function Call的工作流程：

用户输入 → LLM理解意图 → 生成函数调用指令 → 传递给执行层

MCP的工作流程：

可用工具注册 → 协议标准化描述 → 客户端发现工具 → 执行调用请求 → 返回标准化结果

总的来说，Function Call与MCP是AI Agent工具化进程中不同层级的解决方案：

  • Function Call解决”模型想做什么”的问题
  • MCP解决”如何让模型的想法可靠执行”的问题

两者共同构成了AI Agent应用从意图识别到实际执行的完整技术栈，是AI Agent能力落地的重要基础设施。

还有读者可能会问，MCP Server和Skills之间的联系和区别。两者各有优势：

  • Skills：AI Agent原生的工具系统，运行在AI Agent进程内部，延迟极低。Github上有 3,200+ 社区开发的Skills，适合简单的工具调用场景。
  • MCP Server：标准协议，运行在独立进程中，隔离性更强。可以跨平台复用，生态增长迅速。适合复杂工具、需要安全隔离的场景。

总的来说，在一个AI Agent系统中，两者可以同时使用，整合所有可用工具（包括Skills和 MCP Server），AI Agent会根据任务需要自动选择最合适的工具。

7.2 通俗易懂完整讲解A2A（Agent2Agent）的核心基础知识

Agent2Agent（A2A）协议关注的是如何让多个自主的AI Agent有效地一起工作，使得多个AI Agent/子Agent之间可以协同完成任务，而无需直接共享它们的内部记忆、思考或工具。

A2A协议的本质是定义了一套共享的“语言”和“行为准则”，使得不同来源、不同能力的AI Agent能够相互理解、相互协作，共同完成一个单一AI Agent无法完成的宏大目标：

  • 通信语言：如FIPA ACL，定义了消息的格式、含义（如请求、提议、同意、拒绝）。
  • 协商与协调：AI Agent通过对话来分配任务、解决冲突。例如，采用合同网协议：一个管理者智能体“招标”，其他智能体“投标”，最终管理者选择最合适的投标者。
  • 角色与组织：预先定义AI Agent在组织中的角色（如CEO、CTO、算法专家、开发程序员、设计师等）及其职责和权限。
  • 共享记忆与状态管理：维护一个共享的“黑板”或记忆流，记录团队当前的共识、决策和已完成的工作，确保所有成员上下文一致。

  • Agent-to-Agent（A2A）协议：就像一家科技公司内部员工与员工之间的沟通规则和协作流程。它规定了不同部门的同事（如算法部、研发部、市场部、产品部等）如何开会、如何传递文件、如何就一个项目达成共识。其核心是智能体之间的横向协作。

8. 零基础深入浅出讲解AI Agent中RAG（Retrieval Augmented Generation）的核心基础知识

Rocky认为，如果与AI绘画领域做类比的话，那RAG（检索增强生成，Retrieval Augmented Generation）就是AI Agent领域的ControlNet！

8.1 RAG核心基础知识初探

RAG（检索增强生成，Retrieval Augmented Generation） 已成为当前构建大语言模型（LLM）应用的主流方案。

其核心理念清晰：首先从自有垂直领域数据库中检索相关信息，随后将这些信息整合进提示模板，交由大模型进行润色和最终回答生成。

然而，将基础大模型直接应用于实际业务场景时，往往会面临通用模型能力不足的挑战，主要原因包括：

  1. 知识局限性： 主流大模型（如 DeepSeek、文心一言、通义千问等）的知识完全来源于其训练数据，而这些数据主要基于公开网络信息。因此，模型天然缺乏对实时更新、非公开或私有领域数据的认知。
  2. 幻觉问题： 所有深度学习模型，包括大模型，其底层原理均基于数学概率，输出本质上是数值运算的结果。这导致模型在缺乏特定领域知识或不擅长的任务场景下，容易出现看似合理实则错误的输出（即“一本正经地胡说八道”）。
  3. 数据安全性： 企业级应用对数据安全要求极高，尤其是大型企业，几乎无法接受将敏感私有数据上传至第三方平台进行训练或推理的风险。这使得完全依赖通用大模型自身能力的应用方案，必须在数据安全和应用效果之间艰难权衡。

RAG 正是解决上述关键痛点的有效途径。

核心定义：

RAG（Retrieval-Augmented Generation，检索增强生成） = 检索技术 + LLM 提示工程。
例如，当用户向 LLM 提出一个问题时，RAG 会先从多种数据源检索相关知识片段，然后将检索到的信息和原始问题一同整合进提示词（Prompt）中，最终由 LLM 生成答案。

基于 RAG 架构的产品形态多样，涵盖从整合网络搜索引擎的问答服务到利用私有数据的专业应用程序。

技术背景： 早在 2019 年，Faiss 库就实现了高效的向量嵌入搜索技术。如今，RAG 的蓬勃发展显著推动了向量搜索领域的进步。后续涌现的向量数据库初创公司（如 Chroma、Weaviate 和 Pinecone 等），其核心大多基于开源搜索索引引擎（如 Faiss、NMSLIB），并在其基础上增加了文本存储、元数据管理及其他功能组件。

RAG 优势：

  • 提高准确性：通过引用外部知识库，减少幻觉现象。
  • 实时更新：允许模型访问最新信息，解决知识局限性问题。
  • 经济高效：与重新训练模型相比，降低了更新成本。

RAG 执行流程通常分为以下两个阶段：

1.生成索引阶段：这个阶段通常包括文档清理，以及分词也就是将它们拆分为更小的数据块，并把这些数据库转换成向量，最后存储在向量数据库的过程。

2. 检索阶段：使用用户提出的问题，在向量数据库中检索查询的过程。

2. 数据清洗与压缩

  • 自适应长度分割：根据Embedding模型Token上限（如512 tokens），采用滑动窗口策略，设置15%重叠区以保留上下文

8.5 RAG高级组件详解

【Embeddings重新排名和过滤】

在我们进行初步检索后，一般会具有一些局限性。比如有时向量检索基于语义相似度，检索到的段落可能与查询在主题上高度相关，但未必直接包含问题的答案。有时基于关键词的检索（如BM25）可能被文档中频繁出现的次要关键词干扰，返回并不匹配用户意图的结果。有时初步检索为了不遗漏任何可能相关的信息，通常会设置一个较大的top-K（例如，检索20个片段）。这保证了高召回率，但其中必然混杂着大量不精准或冗余的信息，直接塞给LLM会带来噪声和干扰。同时LLM大模型的上下文长度是有限的，我们无法将检索到的所有文档都喂给它。必须在有限的额度内，提供价值最高的信息。

所以我们在使用RAG获得初步检索结果后，通常需要进一步优化，具体方法包括过滤、重新排序或对结果进行某种形式的转换。比如LlamaIndex库中提供了丰富的后处理机制，能够依据多种条件——如相似度分数、关键词匹配、元数据属性等——对检索结果进行筛选。

此外，我们还可以通过Rerank模型来对初步检索的结果重新排列。

在RAG流程中，Rerank（重排序）模型是一个位于“初步检索”和“最终生成”之间的关键后处理模块。它的核心使命是对初步检索到的大量相关文档进行精细化的排序和筛选，将最相关、最高质量的上下文信息提供给大语言模型（LLM），以生成更准确、可靠的答案。我们可以将其理解为一个“智能过滤器”或“精排专家”。

Rerank模型的核心工作流程主要有以下几步：

1. 输入：接收来自初步检索器的“查询-文档对”列表。例如，一个用户查询 `Q` 和初步检索到的Top 20个文档 `[D1, D2, D3, ..., D20]`。

2. 精细化评分：Rerank模型会为每一个`(Q, Dn)`对进行更深层次的交互式计算和相关性评估。它不再仅仅依靠简单的语义嵌入相似度或词频统计，而是分析查询和文档之间更复杂的语义关系。

3. 重新排序：根据计算出的新相关性分数，对原始的文档列表进行降序重排。原本排名第15的文档，如果经模型判断为极度相关，可能会被提升到第1位。

4. 输出：输出一个经过重新排序且通常经过截断（Top-N）的高质量文档列表，将其作为最优质的上下文传递给LLM进行答案生成。

当前一个常见的模式是：“用便宜的向量检索器广撒网（高召回率），再用精准的Rerank模型精捕捞（高精度）”。

总的来说，这一环节处于将检索得到的上下文信息输入至LLM/AIGC大模型生成最终答案之前，是RAG的pipeline质量的关键步骤。

9. AI Agent中Memory机制的核心基础知识零基础深入浅出讲解

在AIGC时代的主流AI Agent系统中，Memory（记忆）机制的核心目标是为AI Agent提供统一的记忆系统，让AI Agent能够存储、检索和利用在过去交互过程中获取的高价值信息，来解决AI Agent在长程交互、多任务执行、多Agent协作场景下的信息管理问题，从而实现跨用户、跨任务、跨Agent的记忆信息提取、复用与共享，最终提升AI Agent系统的上下文处理效率、任务执行准确性和长期学习能力。

当前Memory机制主要分为短期记忆、长期记忆和工具记忆三大类：

AI Agent Memory = Long-Term Memory（LTM） + Short-Term Memory（STM） + Tool Memory（TM）

没有Memory机制的AI Agent系统，就像金鱼一样，只拥有“7秒的记忆”，而拥有Memory机制的AI Agent则可以获得以下的能力：

  • 记住用户偏好：例如，用户在历史对话中说喜欢科幻小说，下次推荐书籍时就可以优先考虑这个类型。
  • 维持对话上下文连贯：例如，进行多轮对话时，能够理解一些名词的指代（如“他”、“她”、“它”、“那个”指的是什么）。
  • 从历史对话中学习经验：例如，在交互中总结过去的成功或失败经验，优化未来的决策和行动。
  • 持续积累先验知识：例如，将新获取的信息存入知识库，供AI Agent长期使用。

9.1 AI Agent的Memory机制初识

Rocky在本章节中通过一个生动的例子，向AI Agent的初学者们趣味讲解AI Agent Memory机制的概念。

我们也可以把AI Agent想象成一个刚刚毕业、超级聪明但患有严重“瞬间失忆症”的实习生。

这个实习生有个特点：

1. 聪明绝顶：我们问他任何问题，他都能基于已有的知识（训练数据）瞬间给出一个非常专业、高质量的回答。

2. 但瞬间失忆：只要我们关闭当前的聊天窗口，下一次打开一个新的窗口问他时，他完全不记得之前和我们聊过任何内容。他每一次都是“从零开始”地和我们对话。

上述这就是没有记忆机制的LLM/AIGC大模型。

它很强，但它的每次对话都是一个独立的“瞬间”，没有连续性，没有上下文关联。这显然无法完成复杂的、需要上下文的任务。

那么，记忆机制是什么呢？

就是给这个聪明的实习生配一个超级助理 + 一个无限空间的档案库。这个助理负责做三件事：

1. 做笔记（短期记忆）：在和我们的一次对话过程中，助理会把我们聊的所有内容都记在笔记本上。这样，当实习生说到后面忘了前面时，助理可以马上把笔记给他看，让他保持对话的连贯性。这个笔记本就是“短期记忆”或“上下文窗口”。但笔记本篇幅有限，记满了就得翻页，可能会忘掉最开始的内容。

2. 写纪要并归档（长期记忆）：一次漫长的对话结束后，助理不会把整整100页的聊天记录都塞进档案库，那样太乱了。相反，助理会提炼这次对话的“核心信息”和“关键结论”，比如：“客户张三，喜欢喝拿铁咖啡，对价格敏感，上次报价A方案未成功”。然后把这个精简的纪要存进档案库。这个提炼和归档的过程就是“长期记忆”的形成。

3. 适时提醒（记忆检索）：当我们再次和实习生聊天，提到“上次那个客户张三”时，助理会立刻心领神会，飞奔到档案库，把所有关于“张三”的纪要档案找出来，递给实习生。实习生看了档案后，就能好像从未失忆一样和我们无缝衔接地聊下去。这个“找档案”的动作就是“记忆检索”。

这个记忆机制（超级助理+档案库）解决了核心问题：让AI Agent拥有了连续性和个性，从而变得真正“智能”和“有用”。

其具体作用体现在四个方面：

1. 保持连续性，完成复杂任务

如果没有记忆机制：我们让AI Agent“帮我想个公司名”，它想了一个。你再说“要听起来科技感强一点”，它可能就懵了，因为它不记得上一句它自己说了什么。我们只能每次都把全部要求重复一遍。

如果有记忆机制：AI Agent会记得它刚才提议的名字，并能基于我们的反馈“科技感强一点”进行优化。理论上它可以陪我们反复讨论一整天，就像一个真正的合作伙伴。

2. 学习用户偏好，提供个性化服务

如果没有记忆机制：每次我们都说“我不吃香菜”，但它每次都会推荐有香菜的菜。因为它记不住。

如果有记忆机制：AI Agent会把我们“不吃香菜”这个信息写入长期记忆档案。下次我们让它推荐菜谱时，它会自动过滤所有含香菜的菜品，直接给我们个性化推荐。

3. 积累知识，自我演进

如果没有记忆机制：AI Agent无法从过去的错误中学习。它这次犯的错，下次还会再犯。

如果有记忆机制：AI Agent可以把“用户纠正了我的一个错误：XXX事件的年份其实是1991年，不是1992年”这个信息存档。下次再被问到相关问题时，它就会检索到这个纠正后的正确信息来回答，从而实现“成长”。

4. 构建身份和上下文

如果没有记忆机制：AI Agent无法扮演一个持续的角色。比如，它今天可以是我们严厉的编程老师，但明天它就不记得这个设定了。

如果有记忆机制：AI Agent可以把“用户希望我扮演一个严厉的编程老师，并且上次指出了他代码中的缩进错误”这个设定存档。下次互动时，它会首先加载这个“严厉老师”的角色设定和之前的教学进度，让体验非常真实和连贯。

组件比喻技术原理（简单版）
AIGC/LLM模型（如GPT）聪明的失忆实习生基于海量数据训练的大型神经网络，能力强大但无状态（Stateless）
短期记忆助理的笔记本上下文窗口（Context Window）。将本次对话的历史直接传递给模型。窗口大小有限（比如128K tokens），太长会遗忘开头或浪费算力
长期记忆档案库里的纪要向量数据库（Vector Database）。将历史对话的核心信息转换成数学向量（一串数字）并存储。需要时通过相似度搜索快速检索
记忆检索助理跑去档案库找资料检索增强生成（RAG）。根据用户当前的问题，去向量数据库里找到最相关的记忆，和问题一起送给模型，辅助它生成回答


9.2 AI Agent中Memory机制原理详解

当前在AI Agent中增加记忆机制有短期记忆、长期记忆以及工具记忆三种模式。

  1. 短期记忆 / 对话记忆(Short-term / Conversation Memory)主要用于维护当前对话/任务的上下文。通常有窗口限制（只记住最近N轮对话，有底层核心AIGC/LLM大模型上下文窗口决定）。
  2. 长期记忆(Long-term Memory)主要在较长时间跨度内存储和回忆重要信息。容量远大于短期记忆，需要通过检索来获取相关信息。长期记忆机制通常与向量数据库(Vector Database)结合，将信息转换为向量嵌入(Embeddings)后进行存储和相似性检索。
  3. 工具记忆 (Tool Memory)：记录AI Agent调用工具（如API、函数）的历史和结果。这对于需要多步执行复杂任务的Agent至关重要，它可以回顾之前的工具调用结果来决定下一步动作。

Memory机制的核心可以简化为两个基本操作：读取（Read） 和 写入（Write）。

  1. 写入（Write）操作在AI Agent完成一次动作（如回复用户、调用工具）后。将有价值的交互信息（如用户输入、AI输出、工具执行结果、自主总结的要点）持久化到存储中（内存、数据库、文件等）。
  2. 读取（Retrieve / Read）操作在AI Agent处理新的输入或开始新任务之前。根据当前的查询（Query）（如用户的新问题），从记忆存储中查找最相关的信息片段。对于长期记忆，通常使用向量相似性检索。将查询也转换为向量，然后从向量数据库中找出与之最相似的记忆向量。

10. AI Agent中Harness Engineering的核心基础知识

AIGC/LLM大模型决定AI Agent“可能有多聪明”，Harness Engineering决定这份聪明能否被稳定地调度、约束、恢复、验证和规模化。Prompt 是一句工作要求，Context 是上下文阶段性材料，Harness 则是把一个聪明但会遗忘、会犯错的大模型，组织成可靠AI Agent生产系统的整套运行机制。

很多团队都经历过一个相似场景。

同一个大模型、同一份需求、同一套工具，在 Demo 里十分钟跑通；换到实际生产环境，任务执行到第 N 步突然中断。重新启动后，AI Agent不知道邮件是否已经发出，于是又发了一遍；它记得“要改代码”，却忘了“不能改变外部 API”；它说测试通过了，实际只运行了最容易通过的那一组；它调用工具没有报错，外部系统却因为超时只完成了一半。

这时，继续升级大模型可能有帮助，却不能自动解决问题。因为真正坏掉的不是某一次推理，而是大模型外面的执行系统：状态没有持久化，工具结果没有沉淀，权限没有边界，工具结果没有统一语义，失败没有归因，完成也没有独立验收。

Harness Engineering 正是在解决这类问题。

Rocky认为，Harness Engineering 真正具备跨周期价值的原因也在这里：大模型会更新迭代，工具框架会被重写，但“如何让一个AI大模型持续、可控地改变确定的现实世界”的整体思想，不会因为AI技术的更新迭代而淘汰。

Harness Engineering说白了，就是给我们的AI Agent搭一套专属「操作系统」。先给所有人砸一个核心公式，记住这句话，我们对AI Agent的理解直接超过行业80%的人：

AI Agent = Model + Harness Engineering

10.1 Harness Engineering原理介绍

总的来说，我们可以把一套AI Agent系统，完完全全想象成我们手里的电脑：

  • 大模型 = CPU，只负责提供原始算力，是那个脑子好使的核心。
  • 上下文窗口 = 内存，只能临时存点东西，一关程序就全没了。
  • AI Agent = 我们电脑里的APP，不管是写代码、做报表还是订机票，是真正要落地干活的。
  • 那Windows、macOS是什么？就是Harness，这套AI Agent的操作系统。

就好比没有操作系统，我们手里哪怕有一块世界顶级的i9芯片，我们也不能直接对着硅片敲PPT、做表格。同样的道理，没有Harness，我们的大模型哪怕再聪明，我们让它连续干8小时的复杂任务，可能也无法稳定、高效、持久的胜任。它中途丢失上下文怎么办？它写了一堆有bug的垃圾代码如何评估？它犯了低级错误自己都意识不到怎么办？

这些问题，没有一个是「换一个更聪明的AI大模型」能解决的。

这就是为什么2026年，Harness成了AI Agent的胜负手：2024年大家还在卷谁的大模型做题更厉害，到了今天，顶级闭源模型之间的智商差距已经微乎其微，同一道题，GPT和Claude的得分差不了几个点。

但我们让它们连续一周、每天8小时落地干活，差距立刻就拉开了。这个差距，从来不在大模型本身，而在大模型外层的Harness Engineering。

但Harness Engineering又不完全等于传统计算机操作系统。它还包含很多更靠近应用和质量工程的能力，例如：

  • 如何向大模型组装当前上下文；
  • 如何定义工具 schema 和错误返回；
  • 如何编排 Planner、Executor、Evaluator；
  • 如何根据任务风险请求人工批准；
  • 如何把失败轨迹变成回归测试；
  • 如何在大模型升级后删除已经不再需要的脚手架。

所以，更准确的理解是：Harness是AI Agent的运行时、控制器、质量系统和治理层的总和。

OpenAI的Codex团队有个数据：他们用Codex做完整的产品，5个月写了100万行代码，零行手写。整个过程里他们发现，瓶颈早就不是「大模型能不能写代码」，而是「人类能不能赶得上审查代码的速度」。

大模型的产出速度，已经远超人类的把控能力了。这时候我们的重点是质量把控、流程约束、风险兜底、经验沉淀——而这些，全都是Harness Engineering要干的事。

总的来说，我们可以把 Agent Harness 定义为：

围绕基础大模型构建的执行控制层。它负责准备上下文、暴露工具、推进生命周期、持久化状态、限制权限、记录轨迹、处理失败、验证结果，并把反馈重新送回下一轮决策。

如果写成一个更严谨的系统表达式，AI Agent 的行为不是模型 MM 的单变量函数，而是：

Outcome=F(M,H,E,T) \text{Outcome}=F(M,H,E,T)

其中：

  • MM 是大模型及其推理能力；
  • HH 是 Harness，包括控制流、状态、工具、权限、评估和恢复；
  • EE 是执行环境及其真实状态；
  • TT 是任务定义、约束和验收标准。

因此，同一个大模型换一套 Harness，结果可能完全不同；同一套 Harness 换大模型，也可能改变最佳工具粒度、上下文策略和验证深度。更严谨的AI Agent 评估应该报告 model–harness pair，而不是把全部得分都归功于大模型。

10.2 Harness Engineering的三根核心支柱模块

总的来说，Harness Engineering的核心永远是三件事：

  1. 评估闭环——AI Agent不能自己给自己打分
  2. 架构约束——约束越多，反而越可靠
  3. 记忆治理——能持续进化的AI Agent，才真正有壁垒

【第一根支柱：评估闭环——AI Agent不能自己给自己打分】

这是Anthropic最核心的看家本领，也是所有Harness的底线。

我们举个生动的例子：我们让一个实习生写一份项目报告，写完我们让他自己评价写得好不好，他大概率会说“还行吧，该写的都写了”。我们永远不能让做事的人，自己给自己当裁判。

AI Agent也是一模一样的道理。

Anthropic把这套方法叫「评估驱动开发」，说白了就是AI Agent版的TDD（测试驱动开发）：先定义清楚什么叫“做得好”，先把验收标准、测试用例写死，再让AI Agent去干活，干完之后，由一个完全独立的评估器来打分。

这个评估器，不是随便看看内容就给分。它会真的去跑流程、测功能：比如AI Agent写了个预订机票的程序，它就真的用Playwright去点按钮、填表单、跑完整的预订流程，完全按照我们定的标准，一条一条测试验证。

这里有个特别有意思的案例：Anthropic的Opus 4.5在做航班预订测试的时候，直接发现了预订政策里的漏洞，找到了一个比人类给的标准答案更省钱、更合规的解法。结果呢？评估器直接判它「任务失败」。

为什么？因为人类写的评估标准里，只认那一个标准答案。AI Agent聪明到能跳出人类的认知找最优解，反而被死板的评估体系扣了分。

这个故事告诉我们两件事：

  1. 今天的大模型，已经聪明到超出绝大多数人的预期了。
  2. 90%的情况下，不是大模型不行，而是对应的Harness Engineering配套能力跟不上。

还有个数据更直接：CORE-Bench测试里，Opus 4.5初始得分只有42%，后来团队只是修复了评分bug、放宽了不合理的评估限制，什么都没改，模型还是那个模型，得分直接跳到了95%。

【第二根支柱：架构约束——约束越多，反而越可靠】

这是OpenAI Codex团队玩到极致的东西，也是最反直觉的一个点。

还是举个生动形象的例子：我们跟新来的开发工人说“代码要分层，架构要规范，UI逻辑不能写进数据库层”，他点头说好，转头就给我们写出一锅乱炖。

靠嘴说、靠文档写规矩，根本没用。真正有用的，是用系统把规则焊死。

OpenAI的做法简单到粗暴，又有效到离谱：把所有的架构规则，全写进linter和CI流程里。只要他的代码违反了分层规则，系统直接给他打回，连人工review的机会都没有。

他们的代码分层是死的：Types → Config → Service → UI，每一层只能依赖上一层，绝对不能反向依赖。这个规则不是写在开发手册里让人自觉遵守的，是写在程序里，机械执行、零容错的。

更绝的是什么？这些检查规则的linter，本身也是Codex自己生成的。AI Agent自己给自己定规矩，然后自己严格遵守。

Martin Fowler看完OpenAI的实践之后，说了一句话，Rocky建议所有做AI Agent的人都刻在电脑上，这个经验也和机器学习领域本质的思想不谋而合：

“增加信任和可靠性，需要约束解空间。这意味着放弃一些「生成任何东西」的灵活性。”

约束越多，反而越可靠。这句话听起来反直觉，但数据不会骗人：

  • LangChain做了一组对照实验，大模型完全不换，只优化Harness的架构约束，Terminal Bench 2.0的通过率直接从52.8%跳到了66.5%；
  • Vercel更狠，直接把AI Agent的工具删掉了80%，结果任务步骤更少、执行速度更快、最终效果反而更好。

“工具越多越厉害”，这是很多人对AI Agent最大的误解。就像我们给一个实习生开了全公司的系统权限，他不仅干不好活，还大概率给我们捅出大篓子。真正高效的执行，永远是在明确的边界里，做精准的动作。

【第三根支柱：记忆治理——能持续进化的AI Agent，才真正有壁垒】

这根支柱，聊的人最少，但长期来看，它是决定AI Agent天花板的核心。

首先我们问一个问题：多个AI Agent共享一个知识库，AI Agent A往里面写了一条错误的经验，AI Agent B读到了，直接当成真理用了，会发生什么？

答案是：一个AI Agent的幻觉，会通过共享知识库，污染整个系统里的所有AI Agent。

这就像公司里，一个老员工把错误的工作方法写进了团队知识库，后面进来的新人全学了这套错的，整个团队的产出只会越来越歪。

那怎么解决？PrismerCloud的做法，给整个行业打了个样：他们做了一套「进化引擎」，Agent的每一次经验，先记录为「信号」，信号经过反复验证、确认有效之后，才能提炼为「基因」，只有「基因」，才能进入正式的知识库，被所有AI Agent调用。

简单说：没被跨周期反复验证过的，都只是道听途说；只有被长期实践证明有效的，才叫知识。

这里有个数据，直接把卷了好几年的prompt engineering按在地上摩擦：

3行基础prompt，加上一套完善的记忆治理系统，效果约等于200行精心打磨的专家prompt。而且前者会越跑越好、持续进化，后者写完的那一刻，就已经固定死了上限。

这意味着什么？意味着未来我们根本不需要熬几个通宵，去抠prompt里的每一个词、写几百行的指令。只要我们的记忆系统做得好，AI Agent会自己在干活的过程中，沉淀经验、修正错误、持续进化。

10.3 AI Agent掉的链子，本质都是Harness Engineering的漏洞

除了上述讲到的这三根支柱，还有一个绕不开的话题，叫「熵对抗」。

什么意思？AI Agent系统跑久了，一定会自然腐化：文档过期了、架构规则被绕过了、知识库里堆了一堆过时的垃圾信息。就像一个公司运转久了，流程会慢慢变形、制度会慢慢松懈、部门墙会越来越厚。

怎么对抗这种腐化？OpenAI的做法，给了所有人标准答案：他们定期跑一个专门的「重构Agent」，只干一件事——扫描整个系统里的文档不一致、架构违规、流程漏洞。

OpenAI有一句话，Rocky认为是整个Harness Engineering的核心心法：

“当AI Agent遇到困难时，我们把它当作信号：找出缺什么，然后反馈到代码库中，始终让Codex自己写修复。”

AI Agent出了问题，不要去修AI Agent，要去修Harness Engineering。

这次它忘了上下文，我们就给它补上下文管理的模块；这次它写了bug，我们就给它加自动校验的规则；这次它用错了工具，我们就给它收紧工具调用的约束。

每一次翻车，都是完善我们这套操作系统的机会。我们的Harness越完善，AI Agent的下限就越高，就越难翻车。

Anthropic的Claude Code + Agent SDK，是目前通用Harness的标杆，核心就是那套评估驱动的方法论，他们已经用这套体系做深度研究、视频创作、全流程开发；OpenAI的Codex，是架构约束的极致实践，百万行零手写代码的“神话”，全靠这套体系撑着。

Rich Sutton写过一篇经典的论文，叫《苦涩的教训》，核心意思是：长期来看，利用计算能力的通用方法，永远会打败人类精心设计的特定方法。

这个教训，在AI Agent领域，正在再一次应验。

Manus团队6个月里，把自己的Harness重构了5次，同样的模型，5种架构，每一次重写，效果都有质的飞跃；LangChain一年里，核心架构重新设计了3次；Vercel直接删掉了Agent 80%的工具，反而迎来了效果的暴涨。

他们都在做同一件事：Build to Delete，为删除而构建。

大家今天熬了好几个通宵写的「聪明prompt」、设计的精巧逻辑，可能明天大模型一升级，就完全没用了。真正能沉淀下来、形成壁垒的，从来不是这些一次性的东西，而是我们的Harness，是这套能持续进化、能沉淀每一次成功与失败的操作系统。

Phil Schmid有一句话，Rocky觉得是2026年AI Agent领域最值得记住的一句话：

竞争优势不再是prompt，而是我们的Harness Engineering捕获的轨迹。同时每次AI Agent的成功和失败，都是训练下一代的数据。

我们的Harness跑得越久，积累的轨迹越多，我们的AI Agent就越强。这个壁垒，不是靠换一个最新的大模型就能追上的。

  • Prompt Engineering，解决的是「说什么」，管的是单次交互的效果；
  • Context Engineering，解决的是「知道什么」，管的是给模型足够的信息支撑；
  • Harness Engineering，解决的是「怎么持续、稳定、大规模地干活」，管的是AI Agent的下限、上限和长期壁垒。

这三个概念经常被写成一条“旧技术淘汰、新技术上位”的时间线。这样的说法方便传播，却不够严谨。Harness Engineering 并没有让 Prompt Engineering 和 Context Engineering 失效，而是把它们纳入了更大的系统边界。

工程层核心问题主要对象典型失败
Prompt Engineering应该怎样向模型表达任务？指令、例子、格式、角色模型误解目标、输出格式漂移
Context Engineering这一轮模型应该看到什么？文件、历史、检索、摘要、工具结果噪声过多、关键约束丢失、上下文过期
Harness Engineering模型应该怎样持续行动并被控制？工具、状态机、沙箱、权限、观测、评估、恢复重复副作用、越权、失控循环、假完成、不可恢复

一个简单问题可以只靠 Prompt；一个需要阅读十份材料的任务需要 Context；一个持续数小时、会写文件、发消息、调用生产 API 的任务，就必须进入 Harness Engineering。

真正的升级不是“从写 Prompt 改成写 Harness”，而是工程优化对象发生了变化：

  1. 从优化一次回答，转向优化完整执行轨迹；
  2. 从让大模型“感觉自己做对了”，转向让环境提供可验证证据；
  3. 从依赖单次上下文，转向维护跨步骤、跨进程和跨会话的真实任务状态；
  4. 从无限增加模型自由度，转向为不同风险配置不同能力边界。

10.4 Harness的七层核心架构

10.4.1 E——Execution Environment，执行环境与沙箱

这一层回答：代码在哪里运行？可以读写哪些目录？CPU、内存、时长和网络有什么限制？失败后环境能否重新创建？

真正的执行环境不是一个 subprocess.run()。它至少需要资源配额、超时、文件边界、进程清理、网络策略、凭证隔离和环境快照。对于高风险任务，还要使用容器、microVM 或远程沙箱降低爆炸半径。

10.4.2 T——Tool Interface，工具接口与协议

这一层回答：模型能看见哪些能力？工具名称、参数、错误和返回值是否适合模型理解？工具很多时如何发现、选择和动态加载？

MCP、Function Calling 或自定义 RPC 只是连接协议。工具是否好用，还取决于语义是否清晰、schema 是否稳定、结果是否足够简洁、错误是否可恢复。

10.4.3 C——Context and Memory，上下文与记忆

这一层回答：当前模型应该看到什么？哪些事实要跨步骤保留？哪些经验可以跨任务复用？信息从哪里来、何时过期、由谁验证？

上下文窗口、会话状态和长期记忆必须分开。把全部日志塞回窗口，不叫记忆治理，只叫把历史噪声重新播放一遍。

10.4.4 L——Lifecycle and Orchestration，生命周期与编排

这一层回答：任务怎样从接收、规划、执行、暂停、恢复走到完成？单 Agent、子 Agent 和人类如何交接？

核心对象不是“消息”，而是状态机：CREATED → RUNNING → WAITING_APPROVAL → RECOVERING → VERIFYING → COMPLETED/FAILED。

10.4.5 O——Observability and Operations，可观测与运行运营

这一层回答：发生了什么？为什么变慢、不稳定或失败？大模型、工具、上下文和策略的哪个版本参与了本次运行？

没有 Trace 的 Agent，出了问题只能读最终对话猜原因；有 Trace 但没有指标、关联 ID 和失败分类，也只是在收集更昂贵的日志。

10.4.6 V——Verification and Evaluation，验证与评估

这一层回答：任务真的完成了吗？失败来自模型、工具、环境、评估器还是任务定义？这次修改有没有破坏旧能力？

验证不仅是给最终答案打分，还要检查环境状态、过程约束、安全门、恢复行为和成本。

10.4.7 G——Governance and Security，治理与安全

这一层回答：Agent 代表谁行动？谁授权？能访问什么？哪些动作必须人工批准？发生事故后能否追责和撤销？

权限、身份、策略、审计和信息流控制不是上线前补的 Guardrail，而是AI Agent行动能力的一部分。

Harness Engineering 很容易产生一种新的泡沫：过去大家售卖“万能 Prompt”，现在开始售卖“万能 Agent 框架”。但开源一套循环、插件系统或 Memory，并不自动形成商业壁垒。

Harness也会过时，越复杂不等于越先进。这是 Harness Engineering 最容易被忽略的另一半。每个 Planner、上下文重置、重试规则、工具限制和 Evaluator 都编码了一个假设：模型目前无法可靠完成某件事，所以系统替它加一层控制。当模型能力提升，这个假设可能失效，旧 Harness 会从保护装置变成额外延迟和错误源。

大模型会持续变强，也会持续降价。工具红利会被平台吸收，Prompt 技巧会被新模型吃掉，今天复杂的 Planner 可能明天就可以删除。但 Harness Engineering 里最本质的东西——状态、边界、证据、恢复、反馈与责任——不会过时。

大模型能力决定上限，Harness Engineering决定下限；而一个AI Agent 产品真正的商业价值，最终取决于它能否在现实世界里把同一件事长期持续做对。
